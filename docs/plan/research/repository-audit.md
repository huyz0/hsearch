## Lucene Rust: use the engine, isolate its release cadence

The workspace contains `lucene-store`, `lucene-index`, `lucene-codecs`, `lucene-search`, analysis crates, FFI, and a test framework. The public README reports working OpenSearch integration and read/write interoperability. This supports choosing it as the requested engine, but does not establish a stable embedding API or hsearch compatibility. Pin the full Git revision and lock dependency resolution. Later release adoption is a deliberate adapter upgrade with a format/behavior matrix, not a floating dependency update. [Workspace](https://github.com/huyz0/lucene-rust/blob/46e280bc2a208544fb36ecd95932e89cd8bc5618/Cargo.toml), [README](https://github.com/huyz0/lucene-rust/blob/46e280bc2a208544fb36ecd95932e89cd8bc5618/README.md).

`Directory::open` returns `Input`; its variants are owned, mmap, shared, and slices, and it implements `Deref<Target=[u8]>`. Outputs expose `FsIndexOutput`. A synchronous adapter cannot turn arbitrary byte-slice dereferences into awaitable range requests. **The remote-input contract needs engine changes or staged full-file downloads.** Never return uninitialized ranges, block a Tokio worker on network faults, or disguise a userfaultfd experiment as a production directory. M02 compares an explicit bounded read-at abstraction against prefetch/materialization and traces the affected codecs. [Directory implementation](https://github.com/huyz0/lucene-rust/blob/46e280bc2a208544fb36ecd95932e89cd8bc5618/crates/lucene-store/src/directory.rs).

`ConcurrentIndexWriter` describes slot-level indexing, ordered delete packets, commit cuts, and caller-owned merge execution. Its header also states that soft deletes and two-phase commit are single-writer features there. Use the actual supported writer mode, preserve mutation ordering, and test the commit/reader boundary rather than assuming concurrency implies distributed transaction support. Existing NRT replication and reader modules are reuse candidates to audit, not a completed distributed hsearch protocol. [Concurrent writer](https://github.com/huyz0/lucene-rust/blob/46e280bc2a208544fb36ecd95932e89cd8bc5618/crates/lucene-index/src/concurrent_writer.rs).

Some orientation text is stale: AGENTS describes an early phase and an older plugin pin while README describes later delivery; the search module's opening comments also describe an old first slice despite a much larger module inventory. The >1 MiB `index_writer.rs` contents endpoint returned no body, so this audit does not claim a full writer review. Contract spikes must navigate actual definitions and tests, with bounded slices or `lsp-cli`, before freezing the adapter.

## Harness lessons: retain mechanisms, change the operating model

Reuse the small entry router, topic-specific instructions, differential fixtures against Java Lucene, crate dependency checks, per-test deadlines, container resource caps, arithmetic/corruption checks, and a single CI result aggregator. The Lucene CI write-up identifies actual duplicated work and cache limitations; its specific historical timings are not hsearch performance targets. [CI analysis](https://github.com/huyz0/lucene-rust/blob/46e280bc2a208544fb36ecd95932e89cd8bc5618/docs/ci.md).

Change three things deliberately. First, use branch/worktree isolation instead of the source project's direct-on-main workflow. Second, enforce hsearch's chosen 90% coverage floors mechanically: the source instructions acknowledge that their advertised per-file 95% rule is reported rather than enforced by the total threshold. Third, use a host-wide **resource allocator** for heavy builds so independent agent coding remains parallel while memory-intensive work stays within capacity. Do not copy a global single-build lock into every capable Linux CI host. [Source instructions and coverage caveats](https://github.com/huyz0/lucene-rust/blob/46e280bc2a208544fb36ecd95932e89cd8bc5618/AGENTS.md).

pstore's harness analysis records review loops consuming large amounts of context and failing to terminate. Adopt a durable round counter, an enforced review budget, delta verification, and the rule that an empty findings list is valid. A cap must stop starting another round; it must never convert an unresolved correctness failure into permission to merge. Validate the counter and stale-verdict rejection with deliberate bad inputs. [Harness analysis](https://github.com/huyz0/pstore/blob/6ddaf56dd0e34862561b63b173ac3de5cfb50fb4/docs/research/09-rust-stack/agent-harness.md).

## pstore: useful substrate evidence, different engine commitments

pstore is object-storage-native and treats RAM/NVMe as cache. Its research uses immutable objects, conditional metadata publication, lanes, grouped writes, cache affinity, and explicit request accounting. These ideas transfer. Its vector-first structures and per-tenant bundling are not automatic fits for Lucene mutable document semantics. The WAL research explicitly marks older sections superseded, and architecture sections still disagree about per-index versus tenant HEAD layout. Resolve the current implementation and evidence ledger before copying a protocol. [Architecture](https://github.com/huyz0/pstore/blob/6ddaf56dd0e34862561b63b173ac3de5cfb50fb4/docs/research/11-design/architecture.md), [WAL research](https://github.com/huyz0/pstore/blob/6ddaf56dd0e34862561b63b173ac3de5cfb50fb4/docs/research/05-storage-engine/write-path-and-wal.md).

M127 offers more concrete transport evidence: separate public and peer identities, typed frames, byte admission before allocation, shared connection limits, deadline propagation, and H2/H3 fallback classification. Reuse the bounded-resource discipline. Start hsearch with HTTP/2 over mTLS; add QUIC only if measured network conditions justify another protocol. Loopback transport measurements there do not predict cloud tails. [M127 architecture](https://github.com/huyz0/pstore/blob/6ddaf56dd0e34862561b63b173ac3de5cfb50fb4/docs/milestones/M127/ARCHITECTURE.md).

## OpenSearch fork: valuable semantics, incomplete low-latency runtime

The shell replaces cluster-manager authority with conditional object registers while reusing the OpenSearch data plane. Its current low-latency progress document explicitly says runtime writes remain object-WAL-durable. The persistent journal foundations are delivered in part, but quorum activation, committed-only serving integration, archival, and fresh search are not all enabled. Do not describe the delivery plan as a shipped system. [Shell](https://github.com/huyz0/OpenSearch/blob/ad254f6439dc4e93f5f00461b85a086e53a3d2da/serverless/README.md), [progress](https://github.com/huyz0/OpenSearch/blob/ad254f6439dc4e93f5f00461b85a086e53a3d2da/serverless/low-latency-progress.md).

The consensus ADR favors bounded physical groups carrying many logical streams after observing per-group resource growth. The semantic lesson is stronger than the Java library choice: separate consensus membership from cache placement, bind activation to an incarnation, and prevent speculative primary state from leaking into readers. Use a Rust consensus library behind the hsearch journal interface; copying Ratis into a native Rust store would create a second runtime. [Consensus ADR](https://github.com/huyz0/OpenSearch/blob/ad254f6439dc4e93f5f00461b85a086e53a3d2da/serverless/low-latency-consensus-adr.md).

The deferred takeover RFC shows why acknowledging a blind WAL record before engine recovery cannot preserve all existing `_seq_no`, `_version`, create, conditional-update, and realtime GET behavior. hsearch must assign its own canonical operation identity and record **resolved operations**, with explicit preparation and dependent-commit barriers. [Takeover RFC](https://github.com/huyz0/OpenSearch/blob/ad254f6439dc4e93f5f00461b85a086e53a3d2da/serverless/rfc-wal-first-takeover.md).

## LSP and automated review

The likely tool meant by “lsp-rust” is the user's Rust-built `lsp-cli`; no separate repository of that exact name was found in the inspected repository listing. It provides `lsp outline`, definitions, references, calls, diagnostics, schemas, pagination, and MCP mode. The inspected README supports Linux/macOS, not native Windows transport. Its Rust diagnostics do not replace `cargo check`. Pin the binary, run inside WSL/container on Windows, isolate daemon state per worktree, and verify the exact CLI schema before scripting it. [lsp-cli](https://github.com/huyz0/lsp-cli/blob/cd9d492f950ab8fb8a9f54e4aea2f72cfd1aab48/README.md).

`autoreview` favors deterministic checks before LLM review and normalizes Clippy findings, but its listed AST/dataflow engines target other languages. Missing analyzers can reduce coverage without failing by default. Use it only after a doctor check proves the required Rust checks ran; otherwise invoke Clippy and the hsearch rules directly. Treat output as evidence tied to a commit, not a merge authority. [autoreview](https://github.com/huyz0/autoreview/blob/6b1a756cb8ac828a68faaf138cbf71a40f42bcf2/README.md).
