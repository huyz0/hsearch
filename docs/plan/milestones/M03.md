# M03: Storage semantics, cost-aware formats and metadata

Generated from `tasks.json`; edit the ledger and run `python docs/plan/tools/plan.py render`.

Status: **planned**. Owner role: storage/consistency.

## Goal

Create a provider-conformant object substrate and formally reviewable commit/publication model.

## Completion prerequisites

M01

Task-level dependencies determine when individual tasks can start. Milestone prerequisites gate completion.

## Definition of done

- Required conditional/range semantics pass against exact RustFS image/topology and startup fails when they do not.
- Metadata/operation formats are bounded, versioned and crash-recoverable; stale writers and unknown outcomes cannot create false commits.
- Publication, pin and GC transition model has exhaustive bounded histories and negative controls.
- Selected metadata granularity passes the M03.08 total-request/fencing gate, including pages/keys/retries and promotion; idle data-plane polling is absent.

### M03.04: Model authority, pins and GC

### M03.08: Implement and qualify the selected fenced domains and packing

Status: **planned**. Owner role: cost/architecture/operations.

Goal: Implement the researched ordered conditional-create WAL, compatible batching and amortized checkpoint protocol, proving the full activation/GC/reader boundary.

Depends on: M02.07, M03.04, M03.02, M03.07.

Deliverables:

- Fenced ordered-slot log prototype with one in-flight append, failure poisoning, own-term establishment, retained fences/tail locator and explicit unknown outcomes
- Same-tenant/key-compatible domains, bounded batching, inline initial wrapped-key format, amortized dirty-only checkpoints and fenced hot-stream promotion
- Payload-plus-head-CAS comparison implementation and complete attempt/page/key/recovery accounting

Validation:

- Model suspend/resume, concurrent membership change, ambiguous CAS, page growth, pin/GC races and promotion crashes
- Sweep sparse/busy/skewed small streams, incompatible crypto policies, metadata-page/envelope overhead, retry and rebuild amplification

Definition of done:

- Selected fenced protocol preserves unique authority, ordered committed identities and bounded replay/discovery across full fault histories; the small planning model is not its runtime proof
- No obligatory per-batch head CAS/key-sidecar PUT, idle polling or cross-tenant shared keys; extra checkpoint/rewrap/activation/retry requests are explicitly counted
- Failure of provider conditional-write or modeled authority/security conformance requires a recorded design revision, not an unreported fallback; production engine/crypto integration is qualified in M04/M05/M06
