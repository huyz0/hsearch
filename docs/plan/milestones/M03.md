# M03: Storage semantics, cost-aware formats and metadata

Generated from `tasks.json`; edit the ledger and run `python docs/plan/tools/plan.py render`.

Status: **planned**. Owner role: storage/consistency.

## Goal

Create a provider-conformant object substrate and formally reviewable commit/publication model.

## Completion prerequisites

M01

Task-level dependencies determine when individual tasks can start. Milestone prerequisites gate completion.

## Definition of done

- Required conditional/range semantics pass against exact RustFS image/topology and startup fails when they do not.
- Metadata/operation formats are bounded, versioned and crash-recoverable; stale writers and unknown outcomes cannot create false commits.
- Publication, pin and GC transition model has exhaustive bounded histories and negative controls.
- Selected metadata granularity passes the M03.08 total-request/fencing gate, including pages/keys/retries and promotion; idle data-plane polling is absent.

### M03.11: Fence commits with a unique per-commit token and probe it across S3 targets

Status: **planned**. Owner role: storage/consistency.

Goal: Close the fencing gap M02.10 found: on RustFS 1.0.4 an If-Match update with identical bytes from a stale version is accepted, so a conditional write is not fenced by content-hash ETag equality.

Depends on: M03.10, M02.10.

Deliverables:

- A commit rule and adapter support so every conditional write that must fence carries a unique per-commit token (a sequence number or nonce inside the body, or a per-commit key), never relying on ETag equality of unchanged content
- A conformance probe, in the shared contract suite, that updates from the same stale version twice with identical bytes and with distinct bytes, and records which stores fence which case
- The probe run against the pinned RustFS, the pinned MinIO image from M03.10 and a real S3 bucket, with the observed outcome recorded beside the M02.10 evidence

Validation:

- The stale-identical-bytes case is a named test that fails (red) against a deliberately unfenced adapter path before the rule exists, then passes with the token rule.
- Each store's observed outcome is recorded; a store that does not fence distinct-body stale updates is a blocking finding for M06's commit protocol, not a footnote.
- Real-S3 run has a frozen envelope (requests, spend) recorded beside the raw output and is labelled provisional if the account or region is not production.
- Normal independent review of the code and the claimed results, and green CI.

Definition of done:

- No commit path accepts a stale conditional write on identical bytes; the per-commit token rule is stated where the commit protocol (M06) consumes it, and the fencing behaviour of RustFS, MinIO and S3 is measured, not assumed.

Evidence:

- [evidence/m02-bench-profile-bulk.md](../evidence/m02-bench-profile-bulk.md): Origin: the M02.10 control and direct probe showed a stale If-Match update with identical bytes accepted on RustFS 1.0.4, and 16 identical-body writers saw zero conflicts. Other S3 implementations were not tested.

Provisional; MinIO and real S3 not run.

### M03.12: Attribute retries and write verbs in the S3 adapter

Status: **done**. Owner role: cost/architecture/operations.

Goal: Make every retry and every write verb the adapter sends visible in the attribution ledger, without ever repeating a write that may have committed.

Depends on: M03.07.

Deliverables:

- A retry policy under the adapter that repeats reads after a throttle, a 5xx or a failed connect, and repeats a write only when no connection was made, with every attempt attributed and flagged and charged to the request budget
- POST (multipart control) attribution through the probe helper and a hairpin path exercised through the adapter

Validation:

- Inject throttling, connection loss, server errors and a lost response under the retry policy and assert attempts, retries and bytes against the scripted provider's transport log
- A write is never repeated after a status or an unknown outcome; a refused connection sends nothing; a retry past the attempt, byte or deadline limit returns the last real failure
- Normal independent review of the code and the claimed results, and green CI.

Definition of done:

- Retries and write verbs are attributed independently of logical calls and no write that may have committed is repeated; what is not done here (real SDK and multipart path, independent transport classification, conflicts under retry, tenant feed, telemetry) is listed with an owner in M03.13 and M08.02

Evidence:

- [evidence/m03-12-retry-attribution.md](../evidence/m03-12-retry-attribution.md): S3Store::with_retry: reads retried after 429, 500, 502-599 or no connection; a write only when no connection was made (a status such as 503 does not prove a write did not commit, so it is returned and the caller replays the same request id through the conditional-write path); never after an unknown outcome. Each attempt attributed and flagged as a retry (3 attempts of one read: 1 call, 3 attempts, 2 retries, 3 HEADs in the provider log); retries charged to the context's attempt and byte budget and the last real failure returned when the budget or deadline is spent; backoff capped at the remaining deadline; POST attributed as a write verb; a hairpin path classified and priced apart; 22 tests in the file, mutations seen red for each rule. Provisional: the retry layer is the adapter's own, no real SDK ran, no real multipart path exists, and the provider log is written in this repo. Remainder: M03.13 and M08.02.

### M03.09: Decide commit-domain sharing under tenant = index

Status: **done**. Owner role: storage/consistency.

Goal: Resolve the open design question in product-requirements conflict 3 before formats freeze: with one tenant per index, may small indexes share a fenced append lane?

Depends on: M02.07, M03.01.

Deliverables:

- Decision record (templates/decision.md) comparing one lane per index, lanes shared by indexes with the same key, residency and durability policy, and shared lanes with per-index payload encryption; each with requests per acknowledged write, idle cost at 10M indexes with 90% idle, blast radius and noisy-neighbour limits
- Rules for revoking one index's key without blocking its lane-mates, and for BYOK indexes, which cannot share a lane unless the payload is separately encrypted per index
- The chosen option written into the M03.03 format inputs, the M03.08 scope and the PR-02 wording

Validation:

- Run the M02.07 trace workloads at 10M indexes (modelled, labelled as such) and a small-index write storm; test revocation of a lane-mate's key on the M03.04 model

Definition of done:

- The decision forbids an idle per-index request, timer or object (PR-01, PR-11), states that cost scaling with active BYOK indexes remains under option B, and forbids any weakening of the per-index isolation and key boundary, and says what it costs
- The id is M03.09 only because ids are stable; it runs before M03.03 and M03.08 implements it

Evidence:

- [decisions/M03.09-commit-domain-sharing.md](../decisions/M03.09-commit-domain-sharing.md): Accepted decision: indexes share a fenced append lane only with an identical policy tuple (key identity, residency, durability profile, format version); option B now (default-key indexes share in groups of at most 1,000, BYOK indexes keep their own lane), option C (per-index payload encryption) recorded as the path once reviewed (trigger: BYOK above about 25%). Modelled at 10M indexes with 90% idle: a lane per index costs about 4x the requests per write and retains 20M fence/tail objects; sharing costs about 0.49 requests per write. A revocable key must not wrap a shared lane (small stand-in model counterexample; not a proof). Deviation from the validation clause: the lane-mate revocation test ran on a stand-in model (lane_model.py) with new synthetic Poisson workloads, not on the M03.04 model (it does not exist yet) or the M02.07 traces; M03.04 carries the histories as a binding deliverable. Costs stated: blast radius of the group size, noisy neighbours bounded not removed, BYOK pays per-index lanes until C.
- [evidence/m03-09-lane-sharing-model.md](../evidence/m03-09-lane-sharing-model.md): Modelled (not measured) lane_model.py comparison of options A/B/C on a steady small-index load and a write storm at PR-01 scale, a BYOK-share sensitivity, a hot-index workload for the promotion rule (share plus volume floor), and a small exhaustive lane-mate key-revocation search with a deliberately broken control and a recovery-policy control; tables generated by the tool, 11 tests. KMS is counted per batch (upper bound) and the 5% BYOK share is an assumption. M03.08 must measure it.
