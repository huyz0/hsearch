# M22: Pinned views, index management and background jobs

Generated from `tasks.json`; edit the ledger and run `python docs/plan/tools/plan.py render`.

Status: **planned**. Owner role: engine/api.

## Goal

Paging, aliases, reindex, by-query jobs and snapshots, all built on pinned views and bounded background jobs.

## Completion prerequisites

M21

Task-level dependencies determine when individual tasks can start. Milestone prerequisites gate completion.

## Definition of done

- A pinned view serves PIT, search_after and scroll; aliases swap atomically; reindex and by-query jobs are resumable, throttled and cancellable.
- A shallow snapshot costs a constant number of requests and is protected from garbage collection until deleted.

## Tasks

### M22.01: Provide pinned views: paging window, search_after, PIT and scroll

Status: **planned**. Owner role: engine/api.

Goal: One mechanism behind OpenSearch's paging shapes (PR-54).

Depends on: M06.04, M06.05.

Deliverables:

- Bounded `from`/`size` window, `search_after`, point-in-time and scroll with OpenSearch request and response shapes, scroll served on the pinned-view mechanism
- A pin per shard view with fixed routing and catalog generation, keep-alive, explicit release or expiry, registered before the id is returned and honoured by garbage collection; pins visible in metrics

Validation:

- Page a large index with search_after during writes: no duplicates or gaps relative to the pinned view; expired and released ids return a clear error; `from + size` over the window is rejected naming the limit; a view survives compaction and restart

Definition of done:

- GC never deletes an object a live pin needs
- Resuming after a node kill on another node is proved with the distributed work in M07.05

### M22.02: Support aliases with atomic swap, and rollover

Status: **planned**. Owner role: engine/api.

Goal: Zero-downtime cutover and explicit index lifecycle (PR-46, PR-34).

Depends on: M03.05, M06.05.

Deliverables:

- Alias actions in one request take effect as one conditional metadata change, so a request sees entirely the old target or entirely the new; write aliases name one write index; alias resolution uses a fixed catalog generation per request
- Rollover on request or on an admitted check, with no timer or poll per index

Validation:

- Continuous reads and writes through an alias during a swap: none fails and none sees a mix; a swap costs a constant number of conditional writes regardless of index size

Definition of done:

- Alias swap cost does not depend on index size or count
- An idle index with a rollover policy costs no requests

### M22.03: Run `_reindex` as a resumable background job

Status: **planned**. Owner role: engine/api.

Goal: Provide the job framework once and use it for reindex (PR-45).

Depends on: M22.01, M21.04.

Deliverables:

- Durable job record, bounded page reads on a pinned view, throttle, progress, cancel and resume, writing through the normal bulk path; optional query and script-free field mapping
- Type changes served by creating the new index with a new mapping and reindexing into it

Validation:

- Reindex a large index under a type change; kill a node mid-job and resume without duplicating or losing documents; throttle respected; cancel stops it; request count follows bytes, not documents

Definition of done:

- The job framework carries no per-document state beyond what the next page needs
- M22.04 and M10.02 reuse this framework and its logical document iterator

### M22.04: Run update-by-query and delete-by-query as bounded jobs

Status: **planned**. Owner role: engine/api.

Goal: Large changes without starving foreground traffic (PR-48).

Depends on: M22.03, M21.06.

Deliverables:

- Evaluation against a pinned view, bounded pages per shard, resume, cancel and progress on the M22.03 framework
- Version check so a document changed since the pinned view is not overwritten or deleted blindly; script-free update bodies only

Validation:

- Delete a large fraction of a big index under foreground load: foreground p99 stays inside the PR-03 bound; kill and resume with no missed or double deletes; a concurrent update of a matched document is detected; job request cost follows bytes written

Definition of done:

- No job raises request cost per document above the normal write path
- A conflict is reported, never silently overwritten

### M22.05: Create shallow snapshots and restore them in the same store

Status: **planned**. Owner role: engine/api.

Goal: Metadata-only snapshots that pin existing immutable objects (PR-50).

Depends on: M06.04, M03.05.

Deliverables:

- Snapshot record referencing the index's segments, manifests and key envelopes, with pins registered before it is returned; constant request count independent of index size
- Same-store restore creating a new index that references those segments and copies nothing up front; same-key only, with joint storage attribution until detached
- Delete releases pins; an object is reclaimed only when no snapshot and no live index references it

Validation:

- Snapshot a large index and count requests; compact and collect garbage after writes and restore byte-identical content; suspend a GC sweep across snapshot creation; delete and check exclusive versus shared objects; revoke an index key and check the snapshot becomes unreadable

Definition of done:

- Request count is constant with index size, and restore is searchable without copying data
- A snapshot of an index with its own key stays under that key; M10.01 adds the quorum-mode tail and M11.06 the portable form
