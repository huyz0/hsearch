# M20: First runnable slice: RustFS, engine and a minimal endpoint

Generated from `tasks.json`; edit the ledger and run `python docs/plan/tools/plan.py render`.

Status: **planned**. Owner role: storage/runtime.

## Goal

Reach a node that ingests with _bulk and answers _search over data held only in RustFS, with the smallest design that is honest about durability, before the deep features.

## Completion prerequisites

M01

Task-level dependencies determine when individual tasks can start. Milestone prerequisites gate completion.

## Definition of done

- An external HTTP client creates an index, bulk-loads documents, searches and reads them back against a real RustFS, and the data survives deleting every local file.
- Every acknowledged write is recovered after kill -9 at each durability boundary; nothing unacknowledged is ever acknowledged.
- The slice states what it lacks (auth, BYOK, multiple nodes, frozen formats). Formats it writes are marked v0 and disposable until M03.03 freezes them; M06 hardens the same path rather than starting again.

## Tasks

### M20.01: Add an S3-compatible object adapter and run it against RustFS

Status: **done**. Owner role: storage/consistency.

Goal: Give hsearch-object a real backend so every later task runs against a store, not only the in-memory double.

Depends on: M03.02.

Deliverables:

- `ObjectBackend` and `MetadataStore` over the S3 API for RustFS, with exact-pinned client dependencies and licence inventory; MinIO as a second target moves to M03.10 because no pinned MinIO image could be pulled
- Conditional create and conditional update mapped to the trait outcomes the M03.02 probe proves available; exact-version range reads, timeouts and cancellation
- Per-operation request counters (GET, PUT, HEAD, LIST, DELETE) and a digest-pinned RustFS compose file for local and CI runs

Validation:

- Run the M03.01 trait contract suite against RustFS and the in-memory double
- No compare-and-set built from GET plus an unconditional PUT; a missing conditional-write capability fails the run instead of falling back

Definition of done:

- The contract suite passes on RustFS and every request is counted by type
- AWS-specific authentication, KMS and cloud tuning stay in M15; this adapter assumes only the S3 subset the probe verified

Evidence:

- [evidence/m03-02-rustfs-probe.md](../evidence/m03-02-rustfs-probe.md): Contract history, simultaneous CAS, replay, identity conflict, bounded resolution, error mapping and budget tests pass against pinned RustFS 1.0.4 (13 integration, 9 unit tests, 95.7% lines). Requests counted by GET/PUT/HEAD/LIST/DELETE. Provisional; MinIO run moved to M03.10.

### M20.02: Open the engine over object-stored segments

Status: **done**. Owner role: engine/architecture.

Goal: Serve immutable Lucene segment files from the object store through a disposable local cache.

Depends on: M20.01, M02.02.

Deliverables:

- First check whether lucene-rust already has a pluggable directory or input hook for whole-file fetch; if not, the smallest additive upstream PR (a new directory implementation behind a new option or crate, nothing that changes existing OpenSearch behaviour) and a pin bump before this task closes. A local wrapper that reimplements engine behaviour is not allowed (PR-53)
- Engine-side directory in `hsearch-engine` that fetches whole immutable files into a bounded local cache; range-native reads arrive later through M04.02
- Cache holds nothing that is not in the store; eviction and loss are always safe

Validation:

- Write segments with the engine, upload them, delete the cache, reopen and search; compare with the local-directory result
- Existing differential fixtures still pass; file fetch counts per open are recorded as provisional

Definition of done:

- Search results over object-stored segments equal results over a local directory, and deleting the cache never changes them
- Only `hsearch-engine` imports Lucene crates; a missing engine feature goes upstream to lucene-rust (PR-53), not into a local workaround

Evidence:

- [evidence/m20-02-object-stored-segments.md](../evidence/m20-02-object-stored-segments.md): Search over remote-backed segments (in-memory remote and real RustFS 1.0.4) equals search over a local directory, including after deleting the cache; no LIST while opening; whole-file fetches only. Needed no upstream change. Provisional; range reads are M04.02.

### M20.06: Lift the engine adapter's research caps behind a scale profile

Status: **done**. Owner role: engine/architecture.

Goal: Let the engine adapter hold, search and reopen 100,000 documents while every existing bounded behaviour and test stays as it is by default.

Depends on: M20.02.

Deliverables:

- A `Limits` value carried by the schema: the documents, operations, retained-history, segment and buffered-document bounds. `Limits::BOUNDED` equals today's constants and stays the default; `Limits::scale()` is opt-in
- Every cap in the adapter, snapshot search, total-hits check, aggregations, query lowering and reopen verification reads the schema's limits instead of a constant
- Under the scale profile retry history is a bounded window; retry identity beyond it is the log layer's job (M20.03), recorded in the module docs

Validation:

- Every existing engine test passes unchanged with the default limits
- A scale-profile test applies, refreshes, searches, commits, reopens and searches 100,000 documents and compares counts, a term search and a sorted page with the expected values
- Without the scale profile the old caps still refuse at exactly the old numbers

Definition of done:

- 100,000 documents are searchable through the adapter under the scale profile, and the default profile's refusals are byte-for-byte the old ones
- No threshold or test was weakened; the scale profile's memory and time are recorded as provisional

Evidence:

- [evidence/m20-06-engine-scale-profile.md](../evidence/m20-06-engine-scale-profile.md): 100,000 documents apply, search (count, term, text, sorted page, get), commit and reopen under Limits::scale(); the default profile refuses at the old numbers and every existing test passes unchanged; an inexact total-hits count past 1,000 was found and fixed. Provisional.

### M20.03: Write path v0: durable bulk, apply, publish and recover on one node

Status: **planned**. Owner role: storage/runtime.

Goal: Acknowledge a write only after it is in the object store, apply it to the engine, publish segments, and rebuild from the store alone.

Depends on: M20.02, M20.06.

Deliverables:

- One writer per index, a log of conditional-create slots in the object store with derived keys, group commit per index, committed receipts and unknown-outcome handling
- Apply committed operations to the engine, flush segments and publish a root object by conditional update; recovery replays the committed tail from the root
- refresh=false and a simple wait_for (ack when searchable); the coalesced forced refresh and the visibility target are M06.07
- Formats carry a v0 marker, are documented as disposable, and are replaced by the M03.03 formats; no sharing of a log between indexes (M03.09 decides that)

Validation:

- Kill -9 before the slot write, after the slot write before the ack, after the ack before apply, and in the middle of a flush; delete all local files and restart each time
- Count requests per bulk and per refresh; no LIST on any read, write or startup path

Definition of done:

- Zero acknowledged writes are missing after the whole fault matrix, and no write that was never acknowledged is reported as acknowledged
- This is the minimal path, not the M06.01 protocol: fencing across owners, multi-node and authority barriers are out of scope here and listed as such in the report

### M20.04: Serve a minimal HTTP endpoint: create index, streamed _bulk, _search, get, _refresh

Status: **planned**. Owner role: storage/runtime.

Goal: Give an external client something to run against.

Depends on: M20.03, M19.

Deliverables:

- `hsearch-node` binary (single process, all roles) with PUT /{index} with a mapping, POST /_bulk, GET /{index}/_doc/{id}, POST /{index}/_search (match, term, range, bool, from/size) and POST /{index}/_refresh
- NDJSON bulk bodies parsed as a stream under a configured buffer for one request, per-item results in order, request byte and item limits from the API profile's example limits; concurrent-bulk memory ceilings and the document size limit are M21.01
- Unknown routes and parameters rejected with structured errors; loopback bind by default and no authentication (M05 adds mTLS and RBAC); real-time get is M21.05
- New `hsearch-node` crate registered in the workspace layering check and the 90% coverage floor, with the HTTP stack exact-pinned and licence-noted; no layering edge outside the rules in AGENTS.md

Validation:

- Plain HTTP client script, not an SDK, against RustFS: bulk 100k documents, search, restart the node, search again; one over each limit is refused
- Compare a query set with the engine differential documents under fixtures/engine-research (not the stale native inputs in fixtures/api/core-v1) where results exist

Definition of done:

- The calls above work against RustFS from outside the process and return the shapes api-compatibility.md promises for the subset
- Nothing in the response claims a feature the node does not implement
