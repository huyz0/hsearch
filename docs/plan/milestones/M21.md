# M21: Document and mapping semantics

Generated from `tasks.json`; edit the ledger and run `python docs/plan/tools/plan.py render`.

Status: **planned**. Owner role: engine/api.

## Goal

Streamed ingestion, bounded mappings and OpenSearch-style document operations on top of the durable store.

## Completion prerequisites

M06

Task-level dependencies determine when individual tasks can start. Milestone prerequisites gate completion.

## Definition of done

- Large documents and bulk bodies stream under a memory cap; mappings are bounded, shared by content hash and evolve online.
- Real-time get, partial update and nested/join documents behave as the product requirements state, or refuse with a named reason.

## Tasks

### M21.01: Stream bulk bodies and enforce document size limits

Status: **done**. Owner role: engine/api.

Goal: Bound memory per request by a buffer, not by document size (PR-16, PR-40).

Depends on: M20.04, M03.03.

Deliverables:

- Streaming NDJSON and document parser with a configured buffer, concurrent large `_bulk` requests and visible backpressure
- Configurable per-index or per-profile document limit with a hard ceiling of 200 MB, structured rejection naming the limit before anything is committed
- Any engine memory that grows with document size is recorded as an upstream lucene-rust gap (PR-53), not worked around

Validation:

- A 200 MB document and a bulk of many large documents under a fixed memory cap with no OOM; a document one byte over the limit is rejected and nothing of it is committed
- Concurrent large bulks with clients that read slowly; peak memory reported against document size

Definition of done:

- Peak memory per request is bounded by the configured buffer in every test
- The default limit is the M02.05 value; the 200 MB ceiling is not raisable by configuration

Evidence:

- [evidence/m21-01-streamed-bulk.md](../evidence/m21-01-streamed-bulk.md): Streamed _bulk under a configured buffer: peak RSS 4.8-8.5 MB with a 1 MiB buffer for a 210 MiB body versus 5.7-7.1 MB for 21 MiB, 0-0.9 MB for one 200 MiB document (8 runs); one-over-limit document refused by name with nothing committed; 429 beyond the node memory budget; throughput unchanged within noise. Provisional, 4-CPU container. The engine caps a field at 8 KiB, so large documents are refused with bounded memory, not ingested; limit is per profile; a mid-body failure leaves earlier batches applied and reports them. Independent review done, findings fixed, CI green.

### M21.02: Store mappings once by content hash

Status: **done**. Owner role: engine/api.

Goal: Make millions of small indexes share mappings instead of carrying one each (PR-43).

Depends on: M03.03, M20.04.

Deliverables:

- Canonical mapping and settings form, content-hash id, immutable mapping objects under the hash, one parsed copy per node
- Authorization form for shared objects: readable only through each index's own authorization, or a form proved not to leak one index's mapping to another's principals
- Mapping change creates a new immutable object under its new hash

Validation:

- Two indexes with the same mapping in different key order share one hash; 1M indexes from 100 mappings give about 100 stored objects and no per-index parsed copy (modelled beyond what runs, labelled)
- Cross-index sharing and hash collision checks, including principals of one index reading another's mapping

Definition of done:

- Stored mapping objects scale with distinct mappings, not with indexes
- No index can read another index's mapping through a shared object

Evidence:

- [evidence/m21-02-shared-mappings.md](../evidence/m21-02-shared-mappings.md): Mappings stored once as hsearch-format MappingObject by content hash; 1,000 indexes from 100 mappings give 100 objects, each written once, and one parsed copy per distinct mapping per node (1M-index figure is a model). Key order does not change the hash; planted, tampered and missing objects are refused; the name v1 is reserved so no index owns the shared prefix. Per-principal authorization tests wait for M05. Provisional. Independent review done, findings fixed, CI green.

### M21.03: Guard field limits and set the dynamic-mapping policy

Status: **done**. Owner role: engine/api.

Goal: Reject mapping explosion whole and let each index choose how unknown fields behave (PR-42).

Depends on: M21.02.

Deliverables:

- Field-count limit (default from M02.05, upper bound configurable), nested depth and nested-objects-per-document limits
- Per-index dynamic setting `true`, `false` or `strict`; structured errors; per-item bulk errors that never partially apply a mapping change

Validation:

- At the limit one more new field is rejected and the mapping is unchanged; strict rejects an unknown field and false ignores it; a bulk with some items over the limit reports per-item errors with the mapping untouched

Definition of done:

- A request that would pass the limit is rejected as a whole
- The limits are sized for the under-100-fields document shape

Evidence:

- [evidence/m21-03-field-limits-dynamic.md](../evidence/m21-03-field-limits-dynamic.md): Field limits and per-index dynamic policy: a create body over the field limit (default 1,000, configurable to 10,000) is refused whole; strict rejects and false drops an unknown field per bulk item with the mapping never changed (verified across a restart); dynamic is in the canonical mapping and strict stays unwritten so existing hashes hold; depth (20) and nested-object (10,000) checks cost 33 ns of a 383 ns document build and are unit-tested but unreachable over HTTP because bulk refuses all nesting. dynamic true is limit-checked but cannot add fields until M21.04; the engine's 14-field cap sits under the 1,000 default. Provisional, 4-CPU container. Independent review done, findings fixed, CI green.

### M21.04: Evolve mappings online

Status: **planned**. Owner role: engine/api.

Goal: Add fields to a live index without losing writes and refuse changes that cannot be made in place (PR-44).

Depends on: M21.03, M06.02.

Deliverables:

- put-mapping and permitted dynamic additions published as a new immutable mapping version; limits from M21.03 applied to each change
- Segments keep opening under the mapping version they were written with; changing a field's type or analyzer is refused with an error that points to a new index plus `_reindex`

Validation:

- Add a field while writes and searches run: no write lost, old segments readable, new field searchable; a type change on an existing field is rejected and the mapping is unchanged

Definition of done:

- Concurrent writers see either the old or the new mapping version, never a mix
- Mapping publication costs a constant number of conditional writes

### M21.05: Serve real-time get and multi-get from the shard owner

Status: **planned**. Owner role: engine/api.

Goal: Return the latest acknowledged write whether or not a reader covering it exists (PR-49, owner side).

Depends on: M06.03.

Deliverables:

- `GET /{index}/_doc/{id}` and multi-get answered from committed-but-unpublished state on the owner, honouring custom routing; `realtime=false` reads published state only
- Multi-get grouped by shard so cost follows shards touched, not documents asked for

Validation:

- Write with refresh=false and read at once; update then get returns the update; delete then get returns not found; the same after owner restart; multi-get of 10 and 20 documents in one shard cost the same requests

Definition of done:

- A get never returns older data than an acknowledged write
- Forwarding through a coordinator and the amortized authority barrier are M07.12

### M21.06: Implement partial update

Status: **planned**. Owner role: engine/api.

Goal: Support `_update` as a best-effort fast path that never compromises durability, visibility, request cost or scale (PR-47).

Depends on: M04.03, M06.01, M21.05.

Deliverables:

- Partial-document merge, `doc_as_upsert`/`upsert`, `detect_noop`, and optimistic concurrency with `if_seq_no`/`if_primary_term` mapped onto the native version token
- The update is resolved once on the shard owner against committed state and the resolved operation is what is logged; replay never re-evaluates it; scripted updates stay out of scope

Validation:

- Concurrent updates: a lost race returns a conflict, never a silent overwrite; crash-replay yields the same document; request count per update equals an index operation; update latency reported against index latency

Definition of done:

- No update adds object-store requests beyond an index operation
- The A02 and A04 matrix rows match the behaviour tested

### M21.08: Index large text fields up to the index's document ceiling

Status: **done**. Owner role: engine/api.

Goal: Let a text field be as large as the write path can hold, with OpenSearch's keyword term limit and a named refusal above the ceiling (PR-40).

Depends on: M21.01.

Deliverables:

- Per-document byte and term bounds are `Limits`, not constants; the research profile keeps its values
- Term counting streams; a keyword over 32,766 bytes is refused whatever the document limit
- Documents of 64 KiB or more are charged their indexing working set against the node memory budget; a spent budget refuses the batch per item with 429
- A document over the ceiling is refused with 413 naming what the build can index

Validation:

- A multi-megabyte text field is indexed, found by a term at its end and returned whole; one byte over the limit is refused; the research profile still refuses beyond 8 KiB
- Peak memory against document size and small-document throughput measured before and after

Definition of done:

- Existing tests pin the research profile unchanged; new tests cover the raised limit
- Measured memory and throughput recorded with their downsides, independent review done, CI green

Evidence:

- [evidence/m21-08-large-text-fields.md](../evidence/m21-08-large-text-fields.md): Text fields up to 4,190,208 bytes indexed, searched and returned whole; keyword term limit 32,766 bytes; streamed term count 4.0 MiB vs 53.9 MiB peak for a 4 MiB field; peak RSS 12.6-16x document size at 1-3.9 MiB, admission-charged at 32x; small-document throughput unchanged within noise. Provisional, 4-CPU container. Independent review done (it found the retained-text and charge gaps, fixed), CI green.

### M21.09: Large-document lane up to the 200 MB ceiling

Status: **done**. Owner role: engine/api.

Goal: Index documents between the index's 4 MiB ceiling and the 100-200 MB product limit with memory bounded by admission (PR-40).

Depends on: M21.08, M03.14.

Deliverables:

- A document over the slot ceiling is written as its own create-only object through the large-object upload seam and referenced from the log, so a slot stays under the object payload bound
- Replay and apply read it back without a second whole-document copy; retry detection by digest instead of an owned copy
- The memory budget charge follows a measured factor for 4-100 MiB documents

Validation:

- A 100 MiB text field is indexed, found by a term at its end and returned whole under a fixed memory cap; a document over the limit is refused and nothing of it is committed
- Peak memory against document size from 4 MiB to 100 MiB, with the downside stated

Definition of done:

- Peak memory is bounded by admission for every size and the charge is no lower than the measured factor
- Any engine memory that grows with document size beyond that is an upstream lucene-rust issue (PR-53)

Evidence:

- [evidence/m21-09-large-documents.md](../evidence/m21-09-large-documents.md): Increment 1: retry history keeps a 128-bit digest instead of an owned copy of each document; peak RSS 16x to 12.7x at 1 MiB and 12.6x to 9.8x at 3.9 MiB, throughput unchanged. Provisional, 4-CPU container. (Superseded: the object lane and the factor were finished in later increments.)
- [evidence/m21-09-large-documents.md](../evidence/m21-09-large-documents.md): Increment 7: 100 MiB document on RustFS indexed, found by its last term, returned byte-equal, peak 567 MiB (5.7x) under the 32x admission charge; one byte over refused 413 with nothing committed; 4-100 MiB sweep 3.7x-5.7x. Engine growth filed as huyz0/lucene-rust#447. Provisional.

### M21.10: Run segment merges off the engine's write lock

Status: **in_progress**. Owner role: engine.

Goal: Remove the remaining refresh stall: a refresh must not wait for a merge, so the visibility p99 holds at larger merge tiers (PR-08).

Depends on: M21.01.

Deliverables:

- Upstream in lucene-rust, as its own pull request: `ConcurrentIndexWriter` accepts hsearch's rich documents, preferably by flushing the inner writer's pending documents under the control lock so `with_writer(update_fields_documents)` is visible to its flush, NRT snapshot and commit; Java-compatible and covered by its differential tests
- The engine adapter writes through `ConcurrentIndexWriter` and runs one bounded merge thread per index inside the index writer thread, with a cap on concurrent merges and their I/O; a panic in native code still poisons the engine and its close, as the poisoned lock did
- The setting is a cluster default overridable per index, and the inline merge stays selectable (`--auto-merge-mb`, the engine default of 0 and every existing test unchanged)

Validation:

- p99 visibility and bytes written measured on RustFS for background merging against the 4 MiB inline merge cap (evidence/m21-11-refresh-merge-tail.md), at 100, 1,000 and 4,000 documents per refresh, three runs each
- A refresh during a running merge returns without waiting for it; segments stay few; a snapshot opened before a merge still answers; close waits for or stops the merge thread

Definition of done:

- Measured p99 and bytes written with their downsides (extra thread and CPU, orphan segments from merges before publish) recorded, independent review done, CI green
- Existing tests pin the inline behaviour unchanged; new tests cover the background mode and run in CI

Evidence:

- [evidence/m21-11-refresh-merge-tail.md](../evidence/m21-11-refresh-merge-tail.md): Cause and the inline fix: with no merge policy a refresh added a segment until the 256-segment cap forced a whole-index merge (1.4 s at 25,000 documents, 3.2 s at 509,000); a tiered merge on refresh at 4 MiB cut the worst call about 2 to 3x at 100 and 1,000 documents per refresh, with 15 to 28% fewer bytes against 16 MiB (not measured against merging off). Still inline under the engine lock. Finding for this task (recorded in that file): lucene-rust's concurrent writer merges refresh-flushed segments and takes a borrowed directory, but has no path for rich documents, and a first swap of the adapter found 0 documents after refresh (4 engine tests failed). Provisional, in-memory store, 4-CPU container.
