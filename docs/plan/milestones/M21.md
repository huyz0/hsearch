# M21: Document and mapping semantics

Generated from `tasks.json`; edit the ledger and run `python docs/plan/tools/plan.py render`.

Status: **planned**. Owner role: engine/api.

## Goal

Streamed ingestion, bounded mappings and OpenSearch-style document operations on top of the durable store.

## Completion prerequisites

M06

Task-level dependencies determine when individual tasks can start. Milestone prerequisites gate completion.

## Definition of done

- Large documents and bulk bodies stream under a memory cap; mappings are bounded, shared by content hash and evolve online.
- Real-time get, partial update and nested/join documents behave as the product requirements state, or refuse with a named reason.

## Tasks

### M21.01: Stream bulk bodies and enforce document size limits

Status: **planned**. Owner role: engine/api.

Goal: Bound memory per request by a buffer, not by document size (PR-16, PR-40).

Depends on: M20.04, M03.03.

Deliverables:

- Streaming NDJSON and document parser with a configured buffer, concurrent large `_bulk` requests and visible backpressure
- Configurable per-index or per-profile document limit with a hard ceiling of 200 MB, structured rejection naming the limit before anything is committed
- Any engine memory that grows with document size is recorded as an upstream lucene-rust gap (PR-53), not worked around

Validation:

- A 200 MB document and a bulk of many large documents under a fixed memory cap with no OOM; a document one byte over the limit is rejected and nothing of it is committed
- Concurrent large bulks with clients that read slowly; peak memory reported against document size

Definition of done:

- Peak memory per request is bounded by the configured buffer in every test
- The default limit is the M02.05 value; the 200 MB ceiling is not raisable by configuration

### M21.02: Store mappings once by content hash

Status: **planned**. Owner role: engine/api.

Goal: Make millions of small indexes share mappings instead of carrying one each (PR-43).

Depends on: M03.03, M20.04.

Deliverables:

- Canonical mapping and settings form, content-hash id, immutable mapping objects under the hash, one parsed copy per node
- Authorization form for shared objects: readable only through each index's own authorization, or a form proved not to leak one index's mapping to another's principals
- Mapping change creates a new immutable object under its new hash

Validation:

- Two indexes with the same mapping in different key order share one hash; 1M indexes from 100 mappings give about 100 stored objects and no per-index parsed copy (modelled beyond what runs, labelled)
- Cross-index sharing and hash collision checks, including principals of one index reading another's mapping

Definition of done:

- Stored mapping objects scale with distinct mappings, not with indexes
- No index can read another index's mapping through a shared object

### M21.03: Guard field limits and set the dynamic-mapping policy

Status: **planned**. Owner role: engine/api.

Goal: Reject mapping explosion whole and let each index choose how unknown fields behave (PR-42).

Depends on: M21.02.

Deliverables:

- Field-count limit (default from M02.05, upper bound configurable), nested depth and nested-objects-per-document limits
- Per-index dynamic setting `true`, `false` or `strict`; structured errors; per-item bulk errors that never partially apply a mapping change

Validation:

- At the limit one more new field is rejected and the mapping is unchanged; strict rejects an unknown field and false ignores it; a bulk with some items over the limit reports per-item errors with the mapping untouched

Definition of done:

- A request that would pass the limit is rejected as a whole
- The limits are sized for the under-100-fields document shape

### M21.04: Evolve mappings online

Status: **planned**. Owner role: engine/api.

Goal: Add fields to a live index without losing writes and refuse changes that cannot be made in place (PR-44).

Depends on: M21.03, M06.02.

Deliverables:

- put-mapping and permitted dynamic additions published as a new immutable mapping version; limits from M21.03 applied to each change
- Segments keep opening under the mapping version they were written with; changing a field's type or analyzer is refused with an error that points to a new index plus `_reindex`

Validation:

- Add a field while writes and searches run: no write lost, old segments readable, new field searchable; a type change on an existing field is rejected and the mapping is unchanged

Definition of done:

- Concurrent writers see either the old or the new mapping version, never a mix
- Mapping publication costs a constant number of conditional writes

### M21.05: Serve real-time get and multi-get from the shard owner

Status: **planned**. Owner role: engine/api.

Goal: Return the latest acknowledged write whether or not a reader covering it exists (PR-49, owner side).

Depends on: M06.03.

Deliverables:

- `GET /{index}/_doc/{id}` and multi-get answered from committed-but-unpublished state on the owner, honouring custom routing; `realtime=false` reads published state only
- Multi-get grouped by shard so cost follows shards touched, not documents asked for

Validation:

- Write with refresh=false and read at once; update then get returns the update; delete then get returns not found; the same after owner restart; multi-get of 10 and 20 documents in one shard cost the same requests

Definition of done:

- A get never returns older data than an acknowledged write
- Forwarding through a coordinator and the amortized authority barrier are M07.12

### M21.06: Implement partial update

Status: **planned**. Owner role: engine/api.

Goal: Support `_update` as a best-effort fast path that never compromises durability, visibility, request cost or scale (PR-47).

Depends on: M04.03, M06.01, M21.05.

Deliverables:

- Partial-document merge, `doc_as_upsert`/`upsert`, `detect_noop`, and optimistic concurrency with `if_seq_no`/`if_primary_term` mapped onto the native version token
- The update is resolved once on the shard owner against committed state and the resolved operation is what is logged; replay never re-evaluates it; scripted updates stay out of scope

Validation:

- Concurrent updates: a lost race returns a conflict, never a silent overwrite; crash-replay yields the same document; request count per update equals an index operation; update latency reported against index latency

Definition of done:

- No update adds object-store requests beyond an index operation
- The A02 and A04 matrix rows match the behaviour tested

### M21.07: Support nested documents and parent-child joins

Status: **planned**. Owner role: engine/search.

Goal: Provide `nested` and `join` fields with their queries, and refuse what would not scale (PR-41).

Depends on: M21.03, M04.01.

Deliverables:

- `nested` fields and queries, `join` fields with `has_child` and `has_parent`, using lucene-rust's block-join support (check parity/joins.md first; gaps go upstream)
- Parent and children routed to the same shard; a child indexed without a routable parent is rejected; a join across shards is rejected, not approximated; limits from M21.03 apply

Validation:

- Nested and join queries match the pinned reference results on a shared corpus; child without routable parent rejected; cross-shard join request rejected with a named reason

Definition of done:

- Matrix rows for nested and join have tests
- Document shape stays under 100 fields; the profile states every difference from OpenSearch
