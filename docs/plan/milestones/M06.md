# M06: Object-durable search store on RustFS

Generated from `tasks.json`; edit the ledger and run `python docs/plan/tools/plan.py render`.

Status: **planned**. Owner role: storage/runtime.

## Goal

Deliver the first complete durable write/search/recovery path using object storage as the sole durable tier.

## Completion prerequisites

M04, M05

Task-level dependencies determine when individual tasks can start. Milestone prerequisites gate completion.

## Definition of done

- Successful mutations survive loss of every compute cache/scratch directory when RustFS and keys remain intact.
- Ordered committed WAL slots and separately published segment/schema roots recover a valid committed prefix; GC cannot delete pinned or unpublished-but-required dependencies.
- An external client can ingest, query, restart, restore and verify a declared dataset on a real RustFS topology.
- Object commits count payload/root/page/key attempts and use dirty-only compatible batching; successful cost reduction preserves restore/freshness semantics.
- M20's v0 log and formats are replaced behind the same endpoint; v0 data is disposable and never migrated.

## Tasks

### M06.01: Implement object-WAL commit protocol

Status: **planned**. Owner role: storage/runtime.

Goal: Acknowledge only authoritative object-durable operations.

Depends on: M04, M05, M03.08, M20.05.

Deliverables:

- Dirty-only group committer, conditional-create ordered WAL slots, inline wrapped-DEK envelope, explicit committed receipts and unknown-outcome resolution
- Structural authority/checkpoint publication separate from append; resolved operation/crypto/schema dependencies validated before the commit PUT

Validation:

- Kill/response-loss at upload/CAS/ack boundaries and concurrent old/new owners with independent receipts.
- Measure dirty-only batching and payload/root/page/envelope attempts under sparse and hot tenants; preserve one authoritative domain per stream.
- Compare the selected one-data-PUT path with payload-plus-head-CAS using the exact same conditional-write/recovery/freshness oracle; include activation, checkpoints, rewrap and strong-read barriers

Definition of done:

- Only the authorized next slot of an established fenced lane commits; an arbitrary uploaded object is never acknowledged
- No later slot follows a failed/ambiguous append; one in-flight append per lane and permanent fence/tail invariants survive reopen/recovery

### M06.07: Implement per-request refresh modes and the visibility target

Status: **planned**. Owner role: storage/runtime.

Goal: Make durable versus searchable a per-request choice and measure it (PR-07, PR-08).

Depends on: M06.05.

Deliverables:

- `refresh=false` (ack when durable), `wait_for` (ack when searchable) and `true` (ack once a reader covering the write is published, forcing a publication if none is due) on bulk, index, update and delete
- Forced publication coalesced across concurrent requests inside one batching window bounded by the profile, never one segment or object per write, and metered per index
- Durable receipts name the committed write even when a visibility wait times out; the batching window is chosen against both the object-durable ack target and PR-08 (conflict 5)

Validation:

- Each mode tested for ack semantics, timeout and lost replies; 1,000 concurrent refresh=true writes cost a number of publications set by the window, not by the writes
- Measure write-ack to first-search-hit at the load, hardware and batch settings frozen in M02.05; report p50 and p99 against < 500 ms and < 5 s as provisional

Definition of done:

- Every mode behaves as PR-07 states and request cost does not scale with the number of refresh=true writes
- The measured visibility latency is reported with its conditions; a miss is recorded, not tuned away by weakening durability
