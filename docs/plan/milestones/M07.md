# M07: Distributed routing and query serving

Generated from `tasks.json`; edit the ledger and run `python docs/plan/tools/plan.py render`.

Status: **planned**. Owner role: query/cluster.

## Goal

Scale query/index roles independently with mTLS and explicit freshness/completeness.

## Completion prerequisites

M06

Task-level dependencies determine when individual tasks can start. Milestone prerequisites gate completion.

## Definition of done

- Multiple nodes accept routed writes and fan out queries with correct document routing, reduce semantics and tenant isolation.
- Latest/at-least/PIT reads validate receiver checkpoints; stale placement cannot downgrade freshness.
- Node loss, hot tenant overload and shard movement preserve declared results or return explicit incomplete/unavailable status.
- Zone-local serving and eligible fallback pass normal and zone-loss cost/capacity tests; direct object access is compared with paid cross-zone peers.
- Core-v1 matching/different/unsupported semantics and total/concurrent work budgets pass early distributed conformance; later migration cannot retroactively define an unbounded API.
- Node roles, fast takeover, graceful drain and coordinator-forwarded real-time get meet the frozen product targets or record their misses (PR-18, PR-29, PR-35, PR-49).

### M07.10: Implement fast failure detection and parallel shard takeover

Status: **planned**. Owner role: query/cluster.

Goal: Make any node's loss recoverable inside the PR-29 targets; the OpenSearch fork's lease design measured p50 59 s, so this is a design task, not a tuning task (PR-29, PR-36, PR-37).

Depends on: M07.03, M07.09.

Deliverables:

- Failure detection that does not depend on a long lease expiry for liveness, compared in a short decision record; ownership is still granted only by conditional write, never by the detector
- Bounded parallel shard activation, preferring a surviving node that already holds the shard's recent data or warm cache; a cold replacement recovers from the object store alone with a bounded warm-up that does not block serving
- Loss of every node in one AZ at once handled inside the same targets, with capacity loss for any index limited to its share of that AZ

Validation:

- Kill -9 a loaded node and then a whole AZ; measure kill-to-first-acknowledged-write per shard against the M02.05 targets; zero acknowledged-write loss; warm and cold takeover reported separately
- Wipe a node's disks and kill it: its shards recover elsewhere with correct data; cold query latency during warm-up reported

Definition of done:

- Takeover meets the frozen targets, or the miss is recorded with its measured cause; a deposed owner never acknowledges
- Searches over the lost node's data keep being served from published state with retries only inside the request deadline

### M07.11: Implement graceful drain with fenced shard handoff

### M07.12: Serve real-time get through any coordinator with an amortized authority barrier

Status: **planned**. Owner role: query/cluster.

Goal: Clients send a get to any coordinator and get the owner's answer (PR-49, routing side).

Depends on: M21.05, M07.05, M07.09.

Deliverables:

- Coordinator resolves the shard, forwards to the owner on the client's behalf, preferring a same-AZ path; direct service from the owner is an optimization
- Get served only under a valid authority barrier; concurrent gets to one shard share one barrier check within a short window; multi-get costs requests by shards touched

Validation:

- Gets sent to a coordinator that does not own the shard return the owner's answers; after owner kill the same holds on the new owner; a get on an owner that lost authority fails or redirects, never answers stale; barrier requests scale with shards and time, not with gets

Definition of done:

- No stale answer from a deposed owner
- Request cost per get does not grow with the number of gets inside a barrier window
