Provisional: one shared x86 VM, synthetic corpus, no ARM; SIFT1M/GIST1M unrun. Independent review found 4 medium items, all fixed before merge of PR 121.

### M23.02: Serve IVF with and without quantization

Status: **done**. Owner role: engine/search.

Goal: Second vector variant (PR-22).

Depends on: M23.01.

Deliverables:

- IVF mapping and query (`nprobe`, rerank) using lucene-rust's `lucene-ivf` and the shared quantizer trait
- Update, delete and merge behaviour of write-once IVF segments stated and tested

Validation:

- Recall@10 and latency on the stated corpus; delete a fraction and merge; compare with HNSW at equal recall

Definition of done:

- Recall@10 meets its floor
- The mapping parameters OpenSearch users set map to a variant or are refused with a reason

Evidence:

- [evidence/m23-02-ivf.md](../evidence/m23-02-ivf.md): IVF with plain, scalar-style (osq2/4/7), BBQ, RaBitQ, extended RaBitQ and auto codes and f32/f16/bf16/int8 rerank through the engine, the durable mapping (method ivf, target_cluster_size, nprobes, rerank_encoding, quantizer) and the knn query (method_parameters.nprobes, filter inside bool). Recall@10 floor 0.90 met for every variant at 8 probed clusters and at the automatic depth on a 3,000-vector corpus; delete, replace, merge and checkpoint reopen of write-once segments tested; OpenSearch ivf parameters map or are refused with a reason. At 50,000 x 128 d IVF builds 4.5x faster than HNSW but is 1.95x larger and 1.9x slower in memory at equal recall, and the automatic probe depth reaches only 0.325 recall there, so nprobes must be set. Provisional: one shared x86 VM, synthetic corpus, no ARM; SIFT1M/GIST1M unrun.

### M23.03: Serve disk-based HNSW and IVF from the object store

Status: **done**. Owner role: engine/search.

Goal: Read vector data by range from the object store instead of loading it (PR-22, PR-53).

Depends on: M23.02, M04.02.

Deliverables:

- Disk-based HNSW (`lucene-disk-hnsw`) and a disk-oriented IVF layout reading by range through the M04.02 input; M02.12 refuted the missing-IVF-layout cell and the pin already has `lucene-ivf` and `lucene-disk-hnsw`, so no bump is needed for them (M02.06 finding 1)
- Cold and warm query reports with range counts per query

Validation:

- Query a corpus larger than the cache cold and warm; count GETs and bytes per query; recall floor holds

Definition of done:

- Range reads per query are bounded and reported, and recall stays above its floor
- No change alters what an existing OpenSearch deployment reads or writes

Evidence:

- [evidence/m23-03-disk-vectors.md](../evidence/m23-03-disk-vectors.md): Disk-based HNSW (lucene-disk-hnsw, page-aligned node records, codes in memory) and IVF read by range through the demand-paged M04.02 input. Mapping `mode: on_disk` plus quantizer, with refusals by name. Cold, warm and steady range counts per query measured on a corpus 1.3x to 3x the cache with a file-backed counting backend; recall@10 stays above 0.90 in every pass. IVF needs 7.5 requests and 2.3 round trips a cold query against 52 and 18 for HNSW; disk HNSW needs more requests than HNSW (72, 38 round trips) and is chosen for memory, not requests. Open reads 0.1 MiB by default; upstream's warm-on-open read the whole 52 MiB, so it is the setting `warm_on_open` (default off). Provisional: one shared x86 VM, synthetic corpus, counting file backend, no ARM; SIFT1M/GIST1M unrun.

### M23.04: Use the calibrated IVF probe depth

Status: **done**. Owner role: engine/search.

Goal: Make an IVF field's default depth the one its segments calibrate, and correct the M23.02 conclusion that it was unsafe (PR-22).

Depends on: M23.02.

Deliverables:

- `nprobes` optional in the IVF mapping; the automatic depth measured at scale on queries like the data and on queries far from every cluster
- A test at hundreds of clusters and the corrected M23.02 evidence

Validation:

- Recall@10 and latency at the automatic depth against fixed depths on both kinds of query; the engine test holds the floor at about 470 clusters

Definition of done:

- A mapping without nprobes is accepted and searches at the calibrated depth, with recall at or above the floor on queries like the data
- The limit for queries far from the data is stated with its measurement

Evidence:

- [evidence/m23-04-ivf-calibrated-depth.md](../evidence/m23-04-ivf-calibrated-depth.md): Upstream calibrates each segment's probe depth when it is written (0.95 recall@10 on a sample of its own vectors). On 50,000 x 128 d queries like the data the automatic depth reaches recall 1.0 at 0.56 ms p50, the cheapest setting; the 0.325 of M23.02 was queries drawn around other centres, where the automatic depth gives 0.27 and 16 probes 0.98. `nprobes` is now optional in the mapping; an engine test at about 470 clusters holds 1.0 against 0.32 at one probe. Provisional: one shared x86 VM, synthetic easy corpus, no ARM; SIFT1M/GIST1M unrun.

### M23.06: Measure vector segment merges at 100k to 1M vectors

Status: **done**. Owner role: engine/search.

Goal: State the merge cost of each vector variant at realistic segment sizes (PR-22).

Depends on: M23.03.

Deliverables:

- A merge benchmark over HNSW, quantized HNSW, disk HNSW and IVF at 100k, 400k and 1M vectors
- Merge time, peak memory, index size and recall after the merge, with the downsides found

Validation:

- Write many segments, force one merge, search the merged segment against exact results; report time, memory and recall per variant

Definition of done:

- Merge time, memory and recall are reported per variant and size, with provisional markings
- Downsides found by the measurement are stated

Evidence:

- [evidence/m23-06-merge-timing.md](../evidence/m23-06-merge-timing.md): IVF merges 7.7x to 10x faster than HNSW at the same size (35k to 85k vectors/s against 6k to 11k; 1M-vector IVF merge 28 s, at most 2.5 GiB above its pre-merge RSS) and merging leaves the index size within 3% and cuts query latency 2.5x to 4x. Recall at a fixed 200 candidates falls after merging every HNSW variant (plain 1.0 to 0.958 at 400k, osq4 disk 0.999 to 0.970 at 100k, bbq 0.94 to 0.50 at 100k) because one graph replaces 12 to 40 walked ones; bbq needs 1,600 candidates for 1.0 at 100k. IVF held 1.0. Measured with an x86-64-v3 build. Provisional: one shared x86 VM, single runs, synthetic corpus; no ARM, no real datasets, no HNSW merge at 1M.

### M23.05: Build the vector kernels with SIMD on x86-64

Status: **done**. Owner role: engine/search.

Goal: Run the AVX2 and FMA distance and code kernels the engine already has, on ARM and x86 (PR-22).

Depends on: M23.03.

Deliverables:

- x86-64-v3 build flags so the compile-time-selected kernels are the SIMD ones, and a startup refusal on a CPU without them
- Measured build and query cost of the SIMD build against the baseline build

Validation:

- Build time, query p50 and recall of HNSW, IVF and disk HNSW variants under both builds; a test fails on a baseline build

Definition of done:

- The x86 build selects the AVX2 and FMA kernels, recall is unchanged, and the measured gain and the CPU floor it sets are stated
- The ARM path is stated as run or unrun

Evidence:

- [evidence/m23-05-simd.md](../evidence/m23-05-simd.md): hsearch built with no target-cpu, so the compile-time AVX2/FMA kernels of lucene-rust ran as scalar code on x86-64. `.cargo/config.toml` now targets x86-64-v3 and the node refuses to start on a CPU without the x86-64-v3 features. At 50,000 x 128 d builds are 25 to 30% faster and IVF queries 1.5x to 2x faster at identical recall; HNSW query p50 is within noise; AVX-512 at run time adds nothing consistent. A test fails on a baseline build. Downside: no CPU older than Haswell without a baseline rebuild. Provisional: one shared x86 VM, single runs, synthetic corpus. ARM (NEON in the aarch64 baseline) is unrun.
