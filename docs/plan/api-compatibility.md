# Scalability-first API contract: core-v1

Status: **design target, not implemented support**. There is no hsearch HTTP/search service yet. The user's 1 November 2026 direction supersedes the earlier broad replacement assumption in R22: prefer useful OpenSearch-inspired compatibility; choose a documented scalable alternative when a semantic is inapplicable or too costly for the selected workload/profile. Durability, security, correctness and truthful completeness remain hard constraints.

The machine-readable [profile](api-profile.json) is the source for the matrix below. **Subset** means a planned, enumerated matching surface; **difference** means intentional native semantics with an adaptation path; **unsupported** means excluded from core-v1. None means a client/server version is already compatible. M02.01 must pin reference releases, client versions, configuration and fixture hashes. A path or similar JSON shape cannot establish SDK compatibility.

Official OpenSearch `latest` docs were consulted on 2026-11-01. Reference facts are linked separately from hsearch design inferences. OpenSearch already supplies useful scalable mechanisms, including PIT/search_after, mapping limits and composite pages. This design does not assert that OpenSearch or every excluded feature cannot scale. Promotion into core-v1 requires measured workload value and bounded cost, not copying every feature or excluding one by reputation.

## Native alternatives and error boundaries

Proposed `/v1` operations are the authoritative native contract. A thin optional adapter accepts only advertised OpenSearch-style routes/options. A capability response lists implemented operations, module/profile revision and effective limits; it must not emit this design matrix as implemented capabilities.

- **Mutation:** stable document ID plus optional opaque `if_version` and scoped idempotency key. Unknown outcomes resolve the original identity. An expired idempotency retention window is explicit; it does not authorize silently treating a retry as a new mutation.
- **Visibility:** writes return durable receipts. `published`, `at_least(receipt)` and authoritative `latest` retain the existing checkpoint contract. An unsuccessful postcommit search wait reports the committed receipt and visibility failure. It cannot imply rollback or acknowledge an unmet visibility promise.
- **Snapshots/pages:** `POST /v1/search-snapshots` accepts an authorized bounded collection/routing scope and TTL. A snapshot binds catalog/routing and a per-partition reader vector, not a globally serializable timestamp. `POST /v1/search-pages` accepts that snapshot, query/sort and an opaque cursor. The cursor binds query/sort and stable document tie-breaks; a snapshot may support a different query with its own cursor. Expiry, revocation or missing generations return typed failure.
- **Large jobs:** scopes beyond interactive work/retention limits use admitted import/export/count/group jobs with bounded batches and durable checkpoints. Paged key-order groups do not reproduce global count-descending ranking. Denormalization does not reproduce arbitrary joins. External analytics or a future module is an explicit application change.
- **Errors:** unknown syntax/options fail explicitly; payload overflow is rejected before unbounded allocation. Bulk structural validation covers the complete bounded request before committing any item. Once execution begins, semantic item failures and committed item receipts are reported individually in request order. No cross-item atomicity or global execution order is promised.

Core-v1 initially uses index/create/delete bulk actions. General `_update`, scripts, external versioning and physical-shard durability controls are excluded. A later native bounded set/remove patch would be a separately specified operation, not an implied OpenSearch deep-merge/upsert implementation.

## Measurable resource and scalability criteria

`example_local_limits` contains illustrative local-development ceilings: 10 MiB/5,000 items per bulk, 512-byte IDs, 1,000 hits/window, 64 total selected partitions, 16 concurrent partition RPCs, 512 buckets, 256 query clauses, five-second interactive deadline and 15-minute maximum snapshot TTL. **These are unmeasured design inputs, not universal release defaults or SLOs.** M02.05/M02.07 must freeze finite per-profile values from workload, hardware and cost evidence. The existing L1/L2/L3/L4 ladder and failure/cost obligations remain in force.

Total selected partitions `S` and concurrent RPCs `F` are distinct. Paging/waves can keep concurrency bounded while total work grows; both need budgets. A request must not scan the full cluster catalog merely to discover that its scope exceeds `S`. Profiles must also bound response/decoded/remote bytes, attempts including retries, queue occupancy, CPU work, active snapshots, retained pin bytes and idempotency state. Snapshot retention charges include GC/merge liability; a TTL alone is not a storage bound. Large scopes use explicit admitted jobs, not a hidden unbounded loop behind an interactive API.

The seven [profile gates](api-profile.json) require cardinality-independence controls, limit+one refusals, distributed admission/cancellation, mutation-safe snapshot paging, honest aggregation accuracy, matched-profile scale/cost curves, and pinned client conformance. All `observed` fields remain false. For G06, M02.05 owns early workload/threshold calibration and freeze, M15.06 supplies real-provider profile curves, and M17.03 owns actual multi-worker service qualification. Early component evidence cannot satisfy that later gate. In particular, growing idle catalog cardinality tenfold at fixed selected work must not introduce a full scan or per-index runtime object; the proposed <=10% hot-request RSS/metadata-attempt growth target must be calibrated and measured with noise reported. It is not an achieved result.

## Ordering and scope changes

[M19](milestones/M19.md) is the new first priority after completed M00. IDs stay stable; its position in the roadmap determines priority, not the number 19. It freezes this direction before API-dependent work. M02 workload/engine and new catalog/budget feasibility then precede format/API freeze. Paged catalog work and observability schemas move earlier; standalone and distributed API conformance/admission gates precede broad migration. [Engineering standards](engineering-standards.md) and the [roadmap](roadmap.md) make these prerequisites executable.

Existing completed bootstrap/sandbox/CI work remains valid. M01.03 is preserved as unfinished local work and must be rebased onto this contract before integration. Copy, CCR, BYOK, mTLS, object/quorum durability, native x86/ARM, >=90% coverage, cost and full release qualification are retained. Out-of-profile OpenSearch workloads block their own migration claim; they do not create an implicit requirement to implement every OpenSearch feature before the declared core can qualify. Releases and deployment remain separately authorized actions.
