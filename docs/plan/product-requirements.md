# Product requirements (authoritative)

Confirmed by Huy on 13 November 2026. These are the product-level requirements AI agents deliver against. Where an older plan document disagrees, this file wins and the conflict is listed in [Conflicts with existing plan documents](#conflicts-with-existing-plan-documents). The older [requirement coverage matrix](requirements.md) (R01-R23) stays as the delivery-evidence index; each `PR-` ID below says which R-IDs it extends.

Targets here are acceptance targets, not measurements. Nothing in this file is claimed as achieved. A number is only reported once a test or benchmark has run, on the hardware named in the report. Per the existing rule, numbers from an emulator or a laptop are relative, not absolute.

## 1. Scale and tenancy

**Tenant = index** (Huy, 13 Nov 2026). One tenant is exactly one index. The index is the unit of isolation, quota, rate limit, metering, cost attribution, authorization scope and BYOK key. There is no tenant that spans many indexes. Where this file or an older plan document says "tenant", read "index". Cross-index grouping for cost (shared commit domains, shared mappings) is an implementation optimization that must never weaken the per-index isolation and key boundary; see the conflicts section.

| ID | Requirement | Testable form |
| --- | --- | --- |
| PR-01 | A deployment holds **10M indexes**. Size is highly skewed: most hold a few documents, a few hold billions, and fewer than 10% are "large". | Catalog and cost model at 10M indexes with 90% or more idle (extends L3 in [performance-scale](performance-scale.md)). No per-index heartbeat, timer, open reader, process or consensus group. |
| PR-02 | Shard count adapts to index size. A small index uses one shard and may share a commit domain with other small indexes only if they have the same key, residency and durability policy (see conflicts: tenant = index). A hot or large index splits online. | Split under write load loses no acknowledged write (M13). A 1-document index costs no steady-state requests. |
| PR-03 | Per-index (tenant) quotas, rate limits and noisy-neighbor isolation. | One index at 10x its quota raises another index's p99 by at most 20% over its unloaded baseline (proposed bound, confirmed in M02). |
| PR-04 | Cold indexes cost nothing while idle (no requests, no compute) and wake within a stated latency. | Idle-cost test: zero request count over an hour. Cold-wake p99 target is set when M02 freezes workloads. |

## 2. Storage and durability

| ID | Requirement | Testable form |
| --- | --- | --- |
| PR-05 | In object mode the remote object store is the only durable tier. Local NVMe (or EBS as a fallback) and RAM are caches. Losing every cache loses no acknowledged data. The optional quorum mode (low-latency writes) additionally needs its journal volumes for the unarchived tail, so its guarantee is RPO <= archive lag; that is a declared exception, not the default. | Object mode: kill all nodes and wipe all local disks; every acknowledged write is recovered from the store. |
| PR-06 | An acknowledged write is never lost. It is in a durable translog/WAL before the acknowledgement. | Fault-injection history: lost replies, node kill, store errors; zero acknowledged writes missing (existing D16 fenced-append design). |
| PR-07 | **Durable versus searchable is a per-request choice**, like OpenSearch `refresh`: `false` (ack when durable), `wait_for` (ack when searchable), `true` (ack once a reader covering this write is published, forcing a reader publication if none is due, but coalesced with other requests so it never costs one segment or object per write). Durable receipts always identify the committed write, even if a visibility wait times out. | Each mode tested for ack semantics, timeout behavior and cost. `true` waits at most one batching window (bounded by the profile) and is metered (see conflicts). |
| PR-08 | **Search visibility after a write: p50 < 500 ms, p99 < 5 s** under the declared benchmark load. | Measured write-ack to first-search-hit latency, reported with load, hardware and batch settings. |
| PR-09 | Storage backends: S3, GCS, Azure Blob, and S3-compatible stores (RustFS first, MinIO). Conditional writes are the only coordination primitive. | Provider capability probe and conformance per provider (existing R04). |
| PR-10 | Snapshot and restore (PR-50, PR-51), and index format versioning with a rolling-upgrade path (PR-52). | Old-format corpus opens in new binaries; mixed-version nodes fail explicitly, never silently. |

## 3. Cost

| ID | Requirement | Testable form |
| --- | --- | --- |
| PR-11 | Minimize object-store **PUT, LIST and GET** requests. No request count may scale with documents, indexes, or idle time. Never LIST on a normal read or write path. | Request-per-operation budgets in CI, as in M02.07/M03.07/M03.08. |
| PR-12 | Minimize **inter-AZ data transfer**. Peers prefer same-zone choices (routing, replica selection, cache fetch), as a preference and never a hard rule. Object-store traffic within a region is not charged by zone, so cold reads go to the store, not to a peer in another zone. | Metered cross-zone bytes per query and per write in the benchmark report. Reference design (read on 13 Nov, branch head 5cd4bb3, not run): the `feature/serverlessshell` branch of huyz0/OpenSearch (`serverless/README.md`, "Keeping traffic inside a zone"): the zone comes from the stock `node.attr.zone` awareness attribute, travels in the node's lease, and an unknown zone counts as neither near nor far. |
| PR-13 | Adding index nodes must not raise request cost per acknowledged write. A shard has one owner at a time, which batches concurrent writes to that shard into shared PUTs; more index nodes spread more shards, not more requests per write. | Requests per acknowledged write at 3x index nodes are within 10% of the 1x figure for the same workload (proposed bound, confirmed in M02). |
| PR-14 | Cost targets ($/GB-month stored, $/million writes, $/million queries) are measured in benchmarks using the [cost model](research/cost-economics.md), not asserted. | Benchmark report includes the cost breakdown by request type and cross-AZ bytes. |
| PR-15 | Per-index cost attribution (requests, bytes, cross-AZ bytes). | Usage records emitted per index; reconcile with the store bill in M15. |

## 4. Throughput and node roles

| ID | Requirement | Testable form |
| --- | --- | --- |
| PR-16 | Many concurrent large `_bulk` requests, streamed rather than buffered whole, with bounded memory per request. | Concurrent-bulk test with a memory ceiling; no OOM, backpressure visible to clients. |
| PR-17 | Many concurrent requests per node, with bounded queues and admission control. | Concurrency sweep with latency curve and explicit 429s past the limit. |
| PR-40 | **Document size is configurable, with a hard ceiling of about 200 MB** per document (default far lower, set per index or profile). Documents and bulk bodies are parsed as a stream: memory per request is bounded by a configured buffer, not by document size. An oversized document is rejected with a structured error naming the limit, before it is committed. | Test a 200 MB document and a bulk of many large documents under a fixed memory cap with no OOM; a document one byte over the limit is rejected and nothing of it is committed. Peak memory is reported against document size. |
| PR-41 | **Documents are shaped for fewer than 100 fields, and the engine supports nested documents and parent-child (join) relationships as OpenSearch does** (`nested` fields and queries, `join` fields with `has_child` / `has_parent`). Where OpenSearch's behavior would break scalability (for example cross-shard joins), the profile must say so and offer a native alternative: parent and children are routed to the same shard, and a join across shards is rejected, not silently approximated. | Compatibility-matrix entries for nested and join with tests. Nested and join queries match the pinned reference results on a shared corpus. A child indexed without a routable parent is rejected. |
| PR-42 | **Mapping explosion is guarded.** A request that would take an index past a configured field limit (default sized for the under-100-fields shape, upper bound configurable) is **rejected** whole, with a structured error. Each index can also set dynamic mapping to `false` or `strict` so unknown fields are ignored or rejected. Nested depth and nested-object count per document are limited too. | Test: at limit, one more new field is rejected and the mapping is unchanged; `strict` rejects an unknown field; `false` ignores it; a bulk with some items over the limit reports per-item errors without partially applying the mapping change. |
| PR-43 | **Mappings are deduplicated and reused, keyed by a content hash.** Indexes with identical canonical mappings and settings share one stored mapping object, and a node holds one parsed copy in memory. A mapping change creates a new immutable object under its new hash. This is part of the cost design: millions of small indexes must not each carry their own mapping blob or in-memory copy. | Canonicalization test: two indexes with the same mapping written in different key order share one hash. At 1M indexes created from 100 distinct mappings, stored mapping objects number about 100 and per-index memory excludes the parsed mapping. Hash collision and cross-index sharing are checked: sharing a stored mapping object between indexes must not leak one index's mapping to another's principals (shared objects readable only through each index's own authorization, or a proven-safe form). |
| PR-44 | **Mapping evolution follows OpenSearch semantics.** New fields can be added to an existing mapping online (put-mapping, or dynamic mapping where allowed). Changing an existing field's type or analyzer is refused with a clear error and done by creating a new index and reindexing. Every mapping change is validated against the PR-42 limits and published as a new immutable mapping version (PR-43). Existing segments keep opening under the mapping version they were written with. | Add-field test with concurrent writes and searches: no write lost, old segments readable, new field searchable. A type change on an existing field is rejected and the mapping is unchanged. |
| PR-45 | **`_reindex` is supported** (index to index, with an optional query and a script-free field mapping), as a resumable, throttled background job that reads in bounded pages and writes through the normal bulk path. It reports progress and can be cancelled. Its request cost is bytes-based, not per-document. | Reindex of a large index under a type change: resumes after a node kill without duplicating or losing documents; throttle limit respected; cancel stops it; request count scales with bytes, not documents. |
| PR-46 | **Aliases are supported, with atomic swaps for zero-downtime cutover.** A single alias-actions request that removes an alias from one index and adds it to another takes effect as one atomic metadata change: a search or write through the alias sees entirely the old target or entirely the new one. Write aliases name one write index. Alias resolution uses a fixed catalog generation within a request (as in architecture.md). | Test: continuous reads and writes through an alias during a swap; none fails and none sees a mix. An alias swap costs a constant number of conditional writes, independent of index size. |
| PR-47 | **Partial update (`_update`) is supported and made fast where it can be, as best effort that never compromises the core requirements** (durability, visibility, request cost, scale). It supports partial-document merge, `doc_as_upsert`/`upsert`, `detect_noop` and optimistic concurrency with `if_seq_no`/`if_primary_term`. The update is resolved to a concrete index operation once, on the shard owner against committed state, and that resolved operation is what is logged; replay never re-evaluates it. Scripted updates are out of scope unless a sandboxed form is separately specified. | Update correctness under concurrent updates (a lost race returns a conflict, never a silent overwrite); crash-replay yields the same document; request count per update equals that of an index operation. Update latency is reported against index latency; no target is set beyond not adding object-store requests. |
| PR-48 | **Update-by-query and delete-by-query are supported as bounded, throttled background jobs**, like `_reindex` (PR-45): evaluated against a pinned point-in-time view, processed in bounded pages per shard, resumable, cancellable, with progress reporting. Speed is best effort; they must not starve foreground traffic or raise request cost per document beyond the normal write path. A document that matched but was changed since the pinned view is not overwritten blindly (version check). | Delete a large fraction of a big index under foreground load: foreground p99 stays within the PR-03 bound, job resumes after a node kill without missing or double-deleting, concurrent update to a matched document is detected, and job request cost scales with bytes written, not with documents matched. |
| PR-49 | **Real-time get by ID, independent of refresh.** `GET /{index}/_doc/{id}` (and multi-get) returns the latest acknowledged write of that document whether or not a reader covering it has been published, as in OpenSearch's realtime GET. The request is routed to the shard's current owner, which holds committed-but-unpublished state; custom `routing` is honoured and decides the shard. **At minimum the ingress or coordinator node serves it**: a client sends the get to any coordinator, which resolves the shard and forwards to the owner on the client's behalf, so clients never need to know which node owns a shard. Serving it directly from the owner is an optimization, not a requirement. The forwarding hop prefers a same-AZ path where the owner allows (PR-39). A realtime get obtains an authority barrier (architecture.md `latest`) so a deposed owner cannot serve stale data. `realtime=false` reads published state only. A multi-get costs requests by the shards touched, not the documents asked for. | Test: send gets to a coordinator that does not own the shard and get the same answers as from the owner. Write with `refresh=false` and read immediately: the value is returned; update then get returns the update; delete then get returns not-found; after owner kill the same holds on the new owner. A get on an owner that has lost authority fails or is redirected, never answers stale. Multi-get of 10 and 20 documents in one shard cost the same number of requests. |
| PR-50 | **Shallow snapshots, valid on the same object store.** A snapshot is a metadata-only record that references the index's existing immutable segments, manifests and key envelopes in the same object store, instead of copying them. Creating one costs a constant number of requests, independent of index size. Every segment a snapshot references is protected from garbage collection until the snapshot is deleted: a pin is registered before the snapshot is returned (architecture.md invariant 6), and compaction or retention never deletes a pinned object. Restore of a shallow snapshot into the same store creates a new index that references those segments and copies nothing up front. Deleting a snapshot releases its pins, and storage is reclaimed only when no snapshot or live index references an object. | Snapshot a large index: request count is constant and independent of size; run compaction and GC after writes: the snapshot still restores byte-identical content; delete the snapshot: its exclusive objects become reclaimable, shared ones do not. Suspend a GC sweep across snapshot creation (the destructive test in architecture.md). Restore does not require copying data to be searchable. A snapshot of an index with its own BYOK key stays encrypted under that key, and revoking the key makes the snapshot unreadable too. |
| PR-51 | **Full portable snapshots for cross-cloud snapshot and restore.** A full snapshot is a self-contained copy of all segments, manifests and metadata that references nothing in the source store. A snapshot taken on one provider (for example S3) can be restored on another (for example GCS or Azure). A shallow snapshot cannot reference objects across stores, so a cross-cloud restore is a **deep copy**: a resumable, throttled background job that streams the referenced objects, verifies checksums and manifests, and creates the index on the destination, reusing the copy machinery of the cross-cluster copy module. The destination must be independent of the source's store after the copy. The cost, mainly cross-cloud egress, is reported before the job starts and metered. The key story is explicit: the destination index is encrypted under a key the destination can reach (same BYOK key through a provider-neutral key interface, or re-encrypted under a new key as in PR-25). | Snapshot on one provider and restore on another through the provider conformance suite (RustFS and a second provider at minimum, real clouds in M15): the restored index returns identical results on a shared query set. The job resumes after a node kill without duplicating or losing objects, reports bytes and request counts, and the destination keeps working after the source bucket is deleted. |
| PR-52 | **Zero-downtime rolling upgrades.** Nodes can be upgraded one at a time (or one AZ at a time) with no service outage: any node may be taken down at any point of a roll, because the object store holds the durable state. A roll uses the graceful drain of PR-35 where it can, and falls back to the abrupt-loss recovery of PR-29 where it cannot. Takeover prefers a surviving node that already holds the shard's recent data or warm cache, and fetches the rest from the object store. Versions N and N+1 coexist during a roll: formats and protocols are versioned, a new node does not write a format an older node in the fleet cannot read until the roll is declared complete, and a node that meets an unknown mandatory capability fails explicitly (architecture.md invariant 10). Rolling back to N is supported until the roll is declared complete. | Roll a loaded 3-AZ fleet from N to N+1 and back: no acknowledged-write loss, no request fails without a retriable error, per-shard write pause within the PR-35 bound, search availability stays at the PR-37 level, and cross-version reads and writes return identical results on a shared corpus. Kill a node mid-roll: recovery meets PR-29. A node that already holds the shard's recent data takes over faster than a cold node, and the benchmark reports both. Old-format corpus from PR-10 opens on N+1. No more than one AZ of capacity is out of service at any time during the roll. |
| PR-18 | **Node roles are declared explicitly in node configuration**: `index`, `search` and `coordinator`, in any combination (a single process may hold all three for development). A node refuses work outside its declared roles with a structured error. Roles scale independently. | Config test: each role alone, each pair, all three. A search-only node never accepts a write. The node reports its roles in its status. |
| PR-19 | **A control plane that spawns or places nodes is out of scope.** The engine must expose what such a control plane needs: declared roles and zone, health and readiness, **scaling metrics per role**, and graceful drain. External orchestrators (Kubernetes and similar) do the spawning and decide when to scale. Index-role metrics include write and bulk ingest rate, queue depth, backpressure and 429 rate, commit and publish lag, active shards and engine memory. Search-role metrics include query rate, p50/p99 latency, queue depth, cache hit rate and fill (RAM and NVMe), cold-read rate and active readers. Coordinator-role metrics include request rate, in-flight requests, fanout width, admission rejections and cross-zone bytes. Every role also reports CPU and memory against its limit. | Status and metrics API contract test, with a named metric set per role in a scrape endpoint (Prometheus format); a test that raising load on one role moves that role's metrics and not another's; drain test with no acknowledged-write loss. |

## 5. API and engine

| ID | Requirement | Testable form |
| --- | --- | --- |
| PR-20 | **OpenSearch API compatibility as close as practical** for full-text and vector search: query DSL, mappings, settings, bulk, search, get. Client libraries do not need to work unchanged. Anything that conflicts with scalability is dropped or replaced with a documented native alternative (for example the `_cat` APIs, replica-count settings, cluster-manager APIs). | Compatibility matrix in [api-compatibility](api-compatibility.md): each route is matching, different or unsupported, with a reason and test. |
| PR-21 | Full-text search through lucene-rust as the core engine (existing D01). | Differential tests against Java Lucene fixtures. |
| PR-22 | **Vector search: HNSW and IVF, each with quantization and with a disk-based variant.** Build on what lucene-rust already provides. | See [Vector support in lucene-rust](#vector-support-in-lucene-rust). Recall@10 floors per variant at a stated corpus. |
| PR-23 | **Extensions follow the OpenSearch extension model, but are Rust or native binaries only, loaded as dynamic modules.** There is no JVM and no scripting-language plugin. A module is a shared library with a **versioned C-compatible ABI, loaded in-process with strict version checks** (decision D18; a separate native process over a versioned RPC is an optional second loading model) that declares its name, version, required engine API version and the extension points it implements (for example analyzers, query types, ingest processors, scoring functions). It is loaded and enabled by explicit node configuration, per node role, and a node refuses to load a module whose declared API version it does not support. A module runs under the same resource limits as core (bounded memory, time and queues), and a module failure disables that module, not the node, wherever the loading model allows. | External example module built outside the workspace, loaded dynamically on a running node, serving a query type and an analyzer; version-mismatch refusal test; disabled-module test; a module that panics or exceeds its limit is isolated and the node keeps serving. Loading is the only place `unsafe` is permitted for this feature: one dedicated loader crate with a written safety proof, and the rest of the workspace keeps `unsafe_code = "forbid"` (D18, conflict 11). |
| PR-54 | **Scroll, paging and point-in-time follow OpenSearch.** `from`/`size` paging, `search_after`, point-in-time (PIT) and scroll are supported with OpenSearch request and response shapes. Deep `from`/`size` is bounded by a configured window; PIT with `search_after` is the recommended path for deep and consistent paging, and scroll is served on top of the same pinned-view mechanism. A PIT and a scroll pin an immutable per-shard view with a fixed routing and catalog generation (not one global instant), have a keep-alive, release explicitly or on expiry, and the pin is registered before the id is returned and honoured by garbage collection. Requests beyond a limit are rejected with the limit named. | Page through a large index with `search_after` while writes continue: no duplicates or gaps relative to the pinned view; a scroll over a pinned view survives compaction and a node kill (resumes on another node); expired and released ids return a clear error; the window limit rejects `from + size` over the bound; pins are visible in metrics so a control plane or operator can see pinned storage.
| PR-53 | **Engine gaps are fixed upstream, not worked around.** Huy owns `huyz0/lucene-rust` and has authorized changing it. When hsearch needs an engine feature the crate lacks (for example a disk-based IVF layout, range-native object-store reads, runtime SIMD dispatch) or hits an engine bug, the fix goes into lucene-rust as its own PR, under that repository's rules (its AGENTS.md, gates, parity ledger and review process), self-reviewed and merged there, and hsearch then bumps its exact pinned revision. hsearch does not carry a private fork, patch, or wrapper that reimplements engine behavior. **Constraint: lucene-rust must remain a drop-in replacement for Lucene inside OpenSearch** (its own goal, served through its FFI). Every change made for hsearch preserves Java-Lucene index-format compatibility, query and scoring semantics and the FFI surface, and is additive: new capabilities sit behind new formats, codecs, options or crates, and never alter what an existing OpenSearch deployment reads, writes or calls. A change that cannot be additive is a conflict to raise with Huy, not to merge. | A hsearch task that needs an engine change links the lucene-rust PR and the new pinned revision; the bridge contract and old-index corpus pass at the new pin (architecture.md, engine integration). `git grep` finds no vendored copy or patch of lucene-rust source in hsearch. Each lucene-rust PR passes that repository's own differential and parity gates, which show Java-compatible output is unchanged; a PR that changes an existing fixture or ledger row as a result is rejected. |

## 7. Replication

| ID | Requirement | Testable form |
| --- | --- | --- |
| PR-28 | Cross-cluster replication (active-passive, follower pull) and same-index replication (PR-25). | Bootstrap, stream, gap, promotion histories (existing R08, D07). The replica's lag is reported, not hidden. |
| PR-29 | **Any node can die at any time and recovery is fast.** Recovery latency may be higher than normal while it happens, but the interval is short and bounded. After an abrupt node loss (kill -9, instance loss), every shard it owned is writable again on another node within **p50 <= 5 s and p99 <= 15 s**, and searches over its data are served by other nodes from published state with no unavailability beyond retries within the request deadline. RPO 0 in object mode. | Fleet fault test: kill a loaded node, measure kill-to-first-acknowledged-write per shard, and verify zero acknowledged-write loss. These are proposed targets to be confirmed or revised when M02 freezes workloads. The OpenSearch fork's own fleet test (read on 13 Nov, not re-run; branch `feature/serverlessshell` at 5cd4bb3, `serverless/scale-test-results.md`) reports kill-to-writable p50 59 s and p99 121 s at a 30 s lease, most of it lease expiry and activation queueing, so meeting this needs a shorter failure-detection design and parallel shard activation. It is a real design target, not a given. |
| PR-35 | **Graceful shutdown hands workload off explicitly.** On drain, a node stops accepting new work for its roles, hands each owned shard to another node with a deliberate fenced transfer (no waiting for a lease to expire), finishes or hands off in-flight requests, and exits when empty or at a deadline. | Drain test under load: per-shard write pause p99 <= 2 s (proposed), zero acknowledged-write loss, zero requests failed without a retriable error, and no node-wide pause. Drain of a node holding N shards completes in a bounded time that is reported against N. A drain that hits its deadline falls back to the abrupt-loss path (PR-29), never to lost data. |
| PR-36 | Recovery does not depend on the dead node's local disk: a replacement node, with cold caches, recovers any shard using only the object store. Cache warm-up after recovery is bounded and does not block serving. | Wipe a node's disks and kill it: its shards recover elsewhere with correct data. Report cold-start query latency during warm-up. |
| PR-37 | **An AZ failure is survivable.** The deployment spans 3 AZs. The external control plane tags each node with its AZ (the stock `node.attr.zone` attribute, as in the fork); the engine reads the tag and never calls a cloud API for it. Losing one AZ must not lose acknowledged data and must not take out a disproportionate share of any tenant's capacity. | AZ-loss fault test with nodes in 3 AZs: kill every node in one AZ at once. Zero acknowledged-write loss; every shard writable again within the PR-29 targets; searches continue from the other two AZs; capacity loss for any index is within its share of the lost AZ (about one third), not more. Object-mode data is already in the regional store, so the test is about serving capacity and ownership, not data copies. |
| PR-38 | **Placement is AZ-aware.** Shard ownership, search replicas and cache copies of one index are spread across AZs so no single AZ holds all of an index's serving capacity. A hot index has serving copies in at least 2 AZs, and an index meeting the profile's availability class has them in all 3. Placement uses node tags only as hints (never to grant authority), and a node with no tag counts as neither near nor far. | Placement test over a 3-AZ fleet at skewed index sizes: no index has all serving copies in one AZ unless its profile says single-AZ economy; spread stays within 1 node of even across AZs for large indexes. |
| PR-39 | **Avoid cross-AZ cost where possible, but never at the price of availability.** Requests are routed to a same-AZ coordinator and same-AZ serving copy when one is eligible; cold data is fetched from the regional object store, which has no cross-AZ charge; peer traffic crosses AZs only when no eligible same-AZ node exists, or for writes whose owner is in another AZ. Cross-AZ replication of cache or data to gain AZ resilience is metered and bounded, and is opt-in per profile because it costs money. | Benchmark reports cross-AZ bytes per query and per write at 3 AZs, split by cause. With all three AZs healthy, steady-state cross-AZ bytes for queries are near zero beyond result-sized responses to an out-of-AZ client; the target figure is set in M02. |

## Conflicts with existing plan documents

1. **Forced refresh.** [api-compatibility](api-compatibility.md) A05 and the architecture text excluded per-request `refresh=true`. PR-07 overrides this: all three modes are supported. Forced visibility is coalesced across requests and metered, so it cannot create one tiny segment or one extra object per write. The architecture text on "per-request forced refresh" must be updated when the API task for A05 lands.
2. **Visibility target.** The SLO worksheet in [performance-scale](performance-scale.md) proposes committed-to-searchable p99 <= 250 ms and has no p50 target. PR-08 adds p50 < 500 ms and relaxes the p99 to < 5 s. PR-08 is the requirement; 250 ms may stay as an internal stretch target.
3. **Tenant = index.** The plan's tenancy model has a tenant owning many indexes (catalog pages, `tenants/<tenant_uuid>/...` layout, commit domains shared "within one tenant", per-tenant admission and quotas in architecture.md, performance-scale.md and the 1M-tenants model). With tenant = index, every one of those becomes per-index: the object layout, authorization, quotas and metering key on the index. The consequence that matters most is commit-domain grouping (D13/D16): the cost design amortizes per-batch and per-checkpoint requests by sharing a fenced append lane among small streams of one tenant, and that no longer has a tenant spanning many indexes to draw on. With 10M mostly-tiny indexes, one lane per index would mean per-index request floors that PR-11 and PR-01 forbid. So M03.08 must decide, before formats freeze, whether indexes with an identical key, residency and durability policy (for example the same deployment-default key) may share a lane across the isolation boundary, and what that costs in blast radius, key revocation (revoking one index's key must not block its lane-mates) and noisy-neighbor limits. Indexes with their own BYOK key cannot share a lane unless the lane payload is separately encrypted per index, which is the open design question. This requirement does not choose; it forbids the per-index floor and the silent weakening of isolation.
4. **Scale figure.** The plan models 1M tenants and up to 50M indexes. PR-01 is 10M indexes. The plan's figure stays a modelled upper bound.
5. **Object-durable ack p99 <= 1 s** (worksheet) and PR-08 interact: with refresh `wait_for`, ack time includes the visibility wait. The batching window must be chosen against both. This is an open tradeoff for M02.07/M03.08, not a settled number.
6. **Control plane.** The plan has maintenance, placement and copy jobs. PR-19 keeps those inside the engine but excludes any component that spawns nodes.
7. **Roles.** [architecture](architecture.md) lists API coordinator, index worker, query worker, maintenance worker and journal. PR-18 uses the user's three names. Mapping: coordinator = API/query coordinator, index = index and maintenance workers, search = query worker. The journal role stays an optional fourth role for quorum mode.
8. **API compatibility wording.** [README](README.md) and [api-compatibility](api-compatibility.md) say full OpenSearch compatibility is not required. PR-20 agrees: "as close as practical" still means the core-v1 profile, with scalability-conflicting features dropped. No change to that profile is intended.
9. **Quorum mode and PR-05.** The optional quorum backend keeps a journal tier for the unarchived tail, so PR-05 is stated for object mode and quorum mode carries its archive-lag RPO.
10. **Query paths.** The fork serves gets from the shard owner while this plan separates query replicas. No conflict, but PR-12 applies to both paths.
11. **Dynamic modules and `unsafe`.** Plan decision D05 promised no native-plugin ABI and the repository forbids `unsafe` (AGENTS.md, workspace lint). Decision D18 (Huy, 13 Nov 2026) supersedes D05's stance: a versioned C-compatible ABI, in-process, strict version checks, with a documented `unsafe` exception confined to one loader crate. Not yet done: the loader crate, its lint exception, the ABI spec and tests are implementation tasks, and the AGENTS.md line "`unsafe` is forbidden" must be amended when the loader crate lands.
12. **Scroll and PIT.** api-compatibility.md A07 lists deep paging, scroll and PIT as differences with native alternatives. PR-54 supports the OpenSearch shapes, built on the pinned-view mechanism already planned, with explicit limits. The matrix row must be updated when that task lands.
