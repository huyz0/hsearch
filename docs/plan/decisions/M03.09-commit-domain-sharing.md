# Decision M03.09: commit-domain sharing under tenant = index

ID M03.09, 14 November 2026, status **accepted (modelled; measured in M03.08)**, owner role storage/consistency.

Question and affected requirements: with one tenant per index, may small indexes share a fenced append lane? Affects PR-01 (10M indexes, 90% idle, no per-index floor), PR-02 (adaptive shards), PR-11 (request budget), PR-06 (no lost acknowledged write) and the isolation and key boundary (product-requirements conflict 3).

Observed evidence and limits: the cost numbers below are **modelled** with the M02.07 batcher and illustrative rate card at the PR-01 scale (10M indexes, 10% active, 5% BYOK, lane groups of 1,000 indexes), not measured; the M02.10 bench measured one PUT per uncontended commit and the hot-key amplification of a head-CAS design, which the fenced append avoids. The revocation model is a small exhaustive search of one lane with two indexes, not the M03.04 authority model (M03.04 does not exist yet and gets this scenario as a deliverable).

`requests per ack` is object PUTs plus KMS wraps per acknowledged write; `retained objects` is the fence and tail-locator objects kept per lane (an assumption of 2 per lane from the M00 design) for every lane that has ever been active; `blast radius` is how many indexes a lane poison or lost fence stalls until recovery. Idle indexes issue **no request in any option** (dirty-only batching, no per-index timer; tested with an empty trace), so the idle difference is retained objects, not requests.

- **A, one lane per index:** about 1.967 requests per write on the steady small-index load against 0.487 when shared, and 2.021 against 0.438 in a write storm: every write is its own batch, so the request count tracks the number of active indexes, not bytes. It also retains 20 million fence/tail objects at 10M indexes. It is the simplest and has no cross-index blast radius, but it **is a per-index request floor in practice**, which PR-01 and PR-11 forbid.
- **B, lanes shared by indexes with the same key, residency and durability policy; a BYOK index keeps its own lane:** about 0.487 requests per write, about 1.0M retained objects and a blast radius of the group size (1,000 indexes). Cost is 25% of A on the steady load. Its weakness is that it degrades toward A as BYOK grows (table below).
- **C, shared lanes with per-index payload encryption (BYOK may share):** about 0.455 requests per write at 5% BYOK, 20,002 retained objects, and the best cost at high BYOK share. It costs a KMS wrap per BYOK record in this upper-bound model, per-index DEK unwraps during lane recovery (bounded by the group size), and a more delicate crypto format that needs the security review (M05) before any code.

## Decision

1. **Shared lanes are allowed.** Indexes may share a fenced append lane only when their **policy tuple is identical: key identity, residency/region, durability profile and format version**. The default for new indexes is the deployment-default key, so the common small index shares. A per-index lane is a fallback, never the default.
2. **Option B now, for default-key indexes; a BYOK index gets its own lane until option C is accepted.** This keeps the cryptography conventional (one lane DEK per batch wrapped by one key) at the price of A's cost for BYOK indexes. At the planned 5% BYOK share B is within 7% of C on requests per write.
3. **Option C is the recorded path, not rejected.** Reconsideration trigger: a deployment where BYOK indexes exceed about 25% of active indexes (B is then 1.7x its 5% cost per write), or retained-object count becoming an operational problem. C then needs the M05 crypto review and a measured recovery-unwrap bound first.
4. **Lane group size is a bounded parameter, default 1,000 indexes**, because the group size is the blast radius. It is a ceiling per lane, enforced when an index joins a lane; hot indexes are promoted to their own lane (the M03.08 fenced hot-stream promotion) when one index exceeds about a quarter of its lane's bytes over a window. In the skewed model (80% of writes to 1% of indexes) the hottest index reached about 10% of a busy lane, so the quarter rule does not fire on that load and does on a true hot index; the number is a starting value for M03.08 to measure.
5. **Revocation rules.** Revoking an index's key never blocks its lane-mates: under B a revocable (BYOK) key is never the wrapper of a shared lane, because the exhaustive model shows the opposite sharing (`lane_dek_a_byok`) makes a lane-mate's records unreadable after `revoke_key_a` (counterexample found in 9 histories: append_a, append_a, append_b, revoke_key_a, recover). Revoking the shared default key is deployment-wide by definition and is a different, intended operation. Under C, `per_index_dek` is safe over all 625 histories: a revoked index's blocks become unreadable and its lane-mates' remain readable after recovery, so lane recovery must skip blocks whose key is revoked rather than fail the lane.
6. **What this costs.** (a) A blast radius of up to the group size: a poisoned or fenced lane stalls its lane-mates' writes until recovery or re-establish. (b) A shared lane means several indexes' encrypted records sit in one object; the record AAD carries the index identity so a record cannot be replayed into another index, and API authorization stays per index, but a compromise of the shared default key exposes all lane-mates, as it already would for the default key. (c) Noisy neighbours are bounded by the promotion rule and per-index admission, not eliminated. (d) BYOK indexes pay the per-index lane cost until option C lands. (e) A membership change (an index adds BYOK, or is promoted) is a lane migration that M03.08 and the M03.04 model must cover.
7. **No per-index floor.** The decision forbids any request, timer or object that exists per index while idle, and forbids weakening the per-index key boundary or authorization to save cost; idle indexes in any option issue no request.

Rejected alternatives and why: A as the default (a per-index request floor in practice and 20M retained objects at scale); C as the default now (the cryptographic format and recovery-unwrap bound are not reviewed or measured, and at 5% BYOK it saves little over B); letting a BYOK index share a lane wrapped by its own key (the revocation counterexample).

Module/format/API/operational consequences: the lane identity in the M03.03 format inputs is the policy tuple plus a group id; record AAD includes the index id; a lane records its member set and group-size ceiling; M03.08 implements membership join/leave and hot-index promotion; M03.04's model includes the lane-mate revocation histories; PR-02 is reworded below.

Migration, rollback and compatibility boundary: formats are not frozen (M03.03 is planned), so nothing is migrated. A later move to option C changes the lane payload format and needs a versioned format and a lane migration.

## Verification

Falsifiable conditions, exact tasks: M03.08 measures requests per acknowledged write on a sparse/busy/skewed small-index sweep against the modelled 0.49 and must stay within 50% of it, measures the largest hot-index share and the promotion behaviour, and measures lane re-establish time after a poison (the blast-radius duration, unmeasured here). M03.04 includes the lane-mate revocation histories. M05 reviews option C before any code. Reconsideration trigger as in decision 3.
