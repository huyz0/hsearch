## Findings

Severity: **blocks M04** = must be settled before M04 starts; **condition** = a task or design correction that M04 or a later milestone carries.

1. **M02.12 is stale: the pin already has IVF, disk HNSW and BBQ/OSQ (condition, schedule correction).** M02.12 says the pin `46e280bc` lacks them and M23.02 and M23.03 need a bump. hsearch has since moved to `17a6254c` (lucene-rust #350). At that rev `crates/` lists `lucene-ivf`, `lucene-disk-hnsw` and `lucene-vector-quant`, and `lucene-util/src/cpu.rs` with `check_baseline` (#307). So M23.02 and M23.03 need no bump for IVF, and M23.03's "where M02.12 confirmed the IVF layout is missing" branch is dead: M02.12 refuted that cell. Fixed in the ledger below. The M02.12 vector tests were run at `46e280bc` and `918cee02`, not at `17a6254c`: M23.01 must rerun them at the pin it builds.
2. **Nothing calls `check_baseline` (condition).** The build baseline is x86-64-v3, so a CPU without it dies with SIGILL and no message (PR-30). `grep` finds no caller in `crates/`. Added to M07.09 (node startup) as a deliverable.
3. **Cold-open evidence counts requests but not round trips (condition C1).** M02.03 measured 41 requests for 33 files at open and 8 for a term query, but not their sequential depth. The project rule is three sequential round trips to rank. M04.02 must report the depth of a cold open and of the first query, and gate it, because PR-04 and PR-31 (cold p99 under 3 s) depend on depth, not count. Open request count also grows with the number of files per segment: report it at gate scale (1M-document partitions), not at 33 files.
4. **`userfaultfd` may not be available where the node runs (condition C2).** The demand-paged path needs it. Recent kernels default `vm.unprivileged_userfaultfd` to 0, so an unprivileged container commonly lacks it (stated from general kernel behaviour, not checked on any target here). lucene-rust #350 adds a spill-file fallback for files of 1 MiB or more, but files under 1 MiB are still read whole onto the heap, and pinned extensions are read whole and may exceed `disk_budget`. M04.02 must (a) detect at startup which path runs and export it as a metric, (b) bound the small-file heap residency per open reader and by concurrently open readers, (c) run its memory-bound test with `userfaultfd` off, since that is the likely production case.
5. **Extra copy and blocked threads on every ranged read (condition C3, trade-off recorded).** `ObjectBlobStore::get_range` copies the payload into the `Vec` the `BlobStore` trait returns, on top of the copy into `Payload` inside `S3Store`: two copies after the network (1 MiB: wrapper adds 61 µs on 123 µs, in-memory backend, provisional). It also blocks the calling thread with `block_on`. This is acceptable for M04.01 and is not hidden. M04.02 must either measure it on RustFS under concurrency and keep it, or land an additive owned-buffer or async `BlobStore` method upstream. Reporting `BlobStore::version` and setting `store_profile` (not yet adopted, M02.03 update) are part of the same task, because without them the page key ignores the manifest version and the read-ahead window is tuned from live latency.
6. **M02.04 left the commit primitive "leading candidate, not selected", while M03.09 and M03.04 build on fenced append lanes (resolved here).** Fenced append (create the next ordered slot) avoids the head CAS whose hot-key cost M02.10 measured (about 1.2 to 1.4 PUT per commit and a 3.6 s p99 under 90% skew). This ADR **selects fenced append lanes** as the object-mode commit design. The CAS-per-commit design is rejected for the write path. The CAS on the lane head stays, but only for establishment, checkpoint and promotion, which are rare.
7. **Fencing correctness depends on a payload token, and only RustFS 1.0.4 has been probed (condition C5).** The ABA and identical-bytes behaviour is real (tests above pass). M03.11 puts a unique token in fencing payloads, which is the right fix. But `If-Match` on an ETag, `If-None-Match`, GCS generation preconditions and Azure ETag semantics are unverified on the real providers: Huy has no AWS S3, so PR-09 conformance on S3, GCS and Azure stays **unrun and is an assumption**, not a result. The design must not rely on provider behaviour beyond "linearizable create-if-absent and compare-and-set on a version token" (it does not), and the conformance probe for each provider stays a release gate for that provider, not for RustFS-first.
8. **The authority model is bounded Python, not the Rust code (condition C6).** 3 instances, 3 records, one checkpoint in the wide run, 2 promoters. Known gaps the model's own notes list: contended establishment, a concurrent join and promotion, descriptor caching, reads racing reclaim. The production rule found by the search ("a successor seals at the first absent slot at or above the checkpoint cover"; fences retained) must exist as a named test in M03.08 and M06.04 that fails without it. M03.08's DoD gets that line.
9. **Group sharing is modelled on an assumed 5% BYOK share (condition C7).** The 0.487 requests per write for option B and the 4x gain over one lane per index rest on it; at 25% B is 0.808, at 100% it equals A. The 1,000-index group size is the blast radius and was chosen, not measured. Both are already stated as assumptions in M03.09 and carry a trigger for option C. Added: M03.08 must report the measured default-key figure per write and the observed lane re-establish time, and the BYOK share assumption goes to Huy only if his real target differs (it is not asked here).
10. **The catalog model proves fixed work at 1,000 vs 10,000 idle collections, not 10M indexes (condition C8).** Its keys are still `(tenant, collection)` pairs. With tenant = index (product-requirements, conflict 3) that key collapses to the index, and the model's per-tenant admission shares become per-index shares. The fixed-work property (two statements, 17 rows, no timers) is a design rule and holds; the RSS ratio is not evidence for 10M. M13 must re-key the model on the index and run its gate at 100x the current idle count before any figure is quoted at PR-01 scale.
11. **No quorum library is selected, but M09 assumes one (blocks M09.01, condition C9).** M02.04 says neither openraft 0.10.0 nor raft-rs 0.7.0 is selected. M09.01 says "the selected Rust library". Evidence supports: no per-index groups (about 7 to 8 idle requests per second per three-member group in both harnesses, 4x10^8 a second at 50M groups, arithmetic), groups multiplexed into bounded physical groups (M09.02), and an object-store-only journal is not what either library offers. M09.01 gets a first deliverable: a recorded library decision with a pinned-rev comparison, which M02.10 also owed. The quorum failover observations (0.7 to 0.95 s for raft-rs, 2.0 to 2.3 s for openraft, one observation each, in-process) are not bounds and do not show PR-29 (p50 5 s, p99 15 s) is reachable; M07.10 must measure it.
12. **PR-08 and the batching window (Question Q1, condition C10).** `object-economy` batches for up to 1 s (p95 batch wait 958 ms in M02.07), which on its own exceeds the 500 ms p50 visibility target for `refresh=wait_for` and `true` unless those modes cut the window short. M02.05 sizes PR-08 on `object-resilient` (250 ms window) only. The two are consistent only if `wait_for` and `true` flush early (coalesced, as PR-07 says) and the cost of that is measured. M06.07 must report requests per write for `wait_for` and `true` on both profiles.
13. **The cost model is an upper bound and says so (no action, recorded).** The Poisson formula overstates bursty batches about tenfold; the rate card is illustrative; KMS is about 37% of object-profile cost under one wrap per batch. PR-24 forbids a KMS call per request, and one per batch is the upper bound the model uses, so a cached lane DEK across batches is the likely real figure. M05.08 owns the measurement. No dollar target is frozen, correctly.
14. **Recovery reachability is open (no action, recorded).** M02.07 and M02.05 use the 120 MiB/s PUT rate as a stand-in for read throughput; GET throughput was never measured. The PR-29 target is therefore unproven, as M02.05 already says. M07.10 owns it.
15. **SIMD.** Compile-time AVX2 and NEON kernels with AVX-512 chosen at run time are confirmed and the measured speedups are large (dot 768 d 6.3x, cosine 8.8x, nibble LUT 35x over scalar, x86 only). **No ARM benchmark exists**, and SVE on Graviton4 is unrun. PR-30 requires both targets: ARM benchmarks run only through the manual ARM workflow (project rule) in M14.03. Until then ARM SIMD claims are limited to "tests pass on arm64 CI".
16. **HNSW at hsearch segment sizes is unrun and concurrent segment search was slower than sequential at 4,000 documents (condition).** Both stay with M23.01 as measure-first, as M02.12 already assigned.

- **C5** (per-provider conformance gate): a provider is supported only after its conditional-write probe passes; RustFS passing says nothing about S3.
- **C6** (M03.08, M06.04): named failing-without-it tests for the cover rule and retained fences.
- **C7** (M03.08): measure requests per write per group, hottest-index share and re-establish time.
- **C8** (M13): re-key the catalog model on the index and rerun at 100x idle count.
- **C9** (M09.01): record the library decision with a pinned-rev comparison first.
- **C10** (M06.07): requests per write and visibility for `wait_for` and `true` on both object profiles.

## Question for Huy

**Q1.** Should the 500 ms p50 and 5 s p99 visibility target (PR-08) bind `object-economy` (1 s batch window, cheapest) or only `object-resilient` and the journal profiles? Recommended: only the latter, with `object-economy` documenting its own visibility figure, because holding it to PR-08 raises its request cost roughly fourfold on busy load (M02.07: 845 vs 3,294 USD per 30 days, illustrative prices). Until answered, this record follows M02.05 and measures PR-08 on `object-resilient`.

## Downsides and trade-offs of what is accepted here

- Reusing lucene-rust's page cache avoids a duplicate cache and its memory and tuning cost, at the price of an extra copy per ranged read and dependence on its read-ahead tuning.
- Fenced append lanes cut requests per write about 4x at the modelled load, at the price of a blast radius of up to 1,000 indexes per lane and a lane migration whenever an index adds BYOK or is promoted.
- Rejecting a consensus group per index keeps idle cost at zero and removes about 4x10^8 idle requests a second at 50M groups, at the price of multiplexing logical streams into bounded groups and of the quorum profiles' separate volume and cross-AZ costs, which are unpriced until M07.14.
