# Decision M02.05: benchmark and failure contracts

ID M02.05, 14 November 2026, status **accepted (contracts frozen; most numbers are targets awaiting measurement)**, owner role engine/architecture.

Question and affected requirements: which workloads, hardware, arrival and receipt rules make a performance claim reproducible, and which proposed numbers in [product-requirements.md](../product-requirements.md) (PR-01, 03, 04, 08, 13, 29, 31, 35, 39, 40, 42) and [performance-scale.md](../performance-scale.md) are frozen now, revised, or left open with an owner.

What this record is and is not: it freezes **protocols and thresholds**. It does not report a qualification. The only measured inputs are single-node, `provisional` ones: the RustFS PUT/CAS bench ([m02-bench-profile-bulk.md](../evidence/m02-bench-profile-bulk.md), two comparable full runs below), the Raft-group envelope runs (M02.10), and the modelled request counts of M02.07 and M03.09. A "frozen" number below is a target the later measurement must meet; where nothing has been measured the row says so. Real-provider curves belong to M15.06 and the G06 service qualification to M17.03; neither is claimed here.

## Baseline reproduced twice

Two fresh back-to-back runs of `crates/s3/examples/bench.rs` against RustFS 1.0.4 (digest-pinned) on the 4-CPU sandbox VM, same commit and binary, raw output and environment in [m02-05-baseline-runs.md](../evidence/m02-05-baseline-runs.md):

| cell | run 1 | run 2 | spread |
|---|---|---|---|
| 1 KiB PUT/s | 223 | 196 | 13% |
| 16 KiB PUT/s | 211 | 188 | 11% |
| 4 MiB PUT/s | 24 | 23 | 4% |
| 64 KiB, 16 writers, PUT/s | 767 | 773 | 1% |
| 64 KiB, 32 writers, PUT/s | 785 | 767 | 2% |
| 4 MiB PUT p99 ms | 103.0 | 109.7 | 6% |
| 16 MiB PUT p99 ms | 518.1 | 182.6 | 2.8x |
| hot-key CAS p99 at 16 writers, ms | 2,359 | 3,047 | 29% |

What this establishes: rates and medians reproduce within about 13%; **tail latency at large payloads and under contention does not** (16 MiB p99 differs by 2.8x between identical back-to-back runs), so no p99 threshold may be judged from five-second cells and every p99 target below is measured over the window in the protocol. The cells hold 30-120 large requests, so none of these p99s meets the protocol's own 10,000-request rule; they are shown only as evidence of instability. What it does not establish: absolute numbers on a reference machine, a real provider, or a cold network path. There is one configuration, so interleaving does not apply, and there is no receipt writer yet: the raw output, commit, image digest and VM record in the evidence file stand in for a receipt, and the receipt design below is not yet in force.

## Workload, hardware and arrival profiles (frozen)

- **Arrival model:** open loop, Poisson arrivals at a stated offered rate, latency measured from the scheduled arrival (the M02.10 open-loop harness does this); closed-loop numbers are labelled as capacity probes only. Offered, completed, rejected and errored requests are all reported.
- **Phases:** 60 s warm-up discarded, 300 s steady state measured, then an overload step and a recovery step reported separately. A p99 over a request stream is reported only from a window with at least 10,000 requests; otherwise the cell reports the max and the count. A p99 on a **fault event** (kill-to-writable, drain pause) is evaluated over at least 200 per-shard samples pooled across repeats, where the p99 is the second-highest; with fewer samples the result reports all samples and the max and is not a pass.
- **Repeats:** at least 3 runs per cell in interleaved order; the reported value is the median with the min-max range, and a rate or median cell whose range exceeds 25% is labelled unstable rather than averaged. A p99 is always shown with its min-max range, and a spread above 25% there (as the large-object p99 below shows) means no p99 target is judged from that window.
- **Workload shapes:** the M02.07 parametric workloads `sparse`, `busy`, `skewed`, `bursty` and `recovery`, and the M03.09 `steady_small`, `write_storm` and `one_hot_index` for small-index sharing. Corpora are pinned by hash.
- **Hardware classes:** `component` is the 4-vCPU sandbox (provisional, relative only); `l1` is 6-12 role-separated Linux nodes in 3 failure domains as in the qualification ladder; `l2` as in the ladder. Every result records CPU model, vCPUs, memory, disk, network, kernel, container limits, and the store (RustFS, MinIO or provider and region).
- **Profiles:** the four operating profiles (`object-economy`, `object-resilient`, `latency-ha`, `latency-zonal`). A target is stated per profile and a cheaper profile does not inherit another's.

## Receipt ledger design (design only, not built)

Every reported result carries a **receipt**: a JSON record with the git commit, binary hash, input-file hash, the full config, machine record, raw histogram or sample file (hash and size), counters (requests by class, bytes, errors), the start and end times and the run's phase boundaries. A table in evidence prose is derived from receipts and cites them; a number without a receipt is `NOT-RUN` for acceptance purposes. The ledger is an append-only directory of receipts plus an index file; a receipt is never edited, a rerun adds a receipt. Independence: the receipt is produced by the harness, not by the code under test, and the reviewer recomputes at least the headline numbers from the raw samples. Building the writer is part of the first milestone that needs a gated number (M06/M07); no new gate is added here.

## Capacity model (frozen form)

- **Requests:** counts per acknowledged write come from `cost_calibration.py` (batching under the profile's window and byte triggers, checkpoint amortisation 2 PUTs per 64 object writes, KMS per batch as an upper bound) and `lane_model.py` for lane sharing. The model is an upper bound for bursty traffic and is checked against measured counts within 50% before any request budget is gated.
- **Throughput per process:** component measurement, not extrapolation: about 710 small (64 KiB) PUT/s completion limit and no queueing knee found up to about 120 MiB/s offered for large payloads on the component VM. These are the single-process object-store client limit; fleet capacity multiplies by nodes only after the M17.03 curve.
- **Memory:** a configured per-request buffer and a node RSS budget below the container limit; a tracked logical buffer sum is not an RSS bound (performance-scale.md). RSS is measured, not summed.

## G06 thresholds (initial tolerances: chosen here, not derived from a calibration)

Scale-efficiency, latency and cost thresholds for the G06 qualification, each to be measured on the implemented service at increasing worker counts in M17.03. Only the PR-13 figure and the latency rows come from the requirements and worksheet; the model-gap and cost tolerances below are tolerances this record picks, with no calibration behind them, and change only with evidence:

| threshold | value | basis |
|---|---|---|
| Requests per acknowledged write at 3x index nodes | within 10% of the 1x figure (PR-13) | M02.07/M03.09 models: lane and batch counts depend on active streams and bytes, not on node count |
| Requests per acknowledged write against the model | measured at most 1.5x the modelled figure for the same profile and workload (the model is an upper bound for bursty traffic, so under-prediction is the failure); below 0.5x is flagged as a model finding, not a failure | M02.07 and M03.09 inputs are modelled |
| Latency | the SLO worksheet rows below, per profile, at at most 70% sustained bottleneck utilisation | performance-scale.md |
| Cost | measured cost per million acknowledged writes, per profile, within 1.25x of the model run on measured counts at the provider's captured prices | an initial tolerance, not sourced; no dollar target is frozen because prices are captured at qualification time |

No claim of an implemented multi-worker service is made by freezing these.

## Performance-scale targets

The SLO worksheet rows in performance-scale.md are **accepted unchanged** as targets, **not as measured results (none is backed by a measurement here)** for the L1 profile they name, with these clarifications and no hidden exclusions: dependency-caused unavailability is reported separately, never excluded; a cold test relabelled warm is invalid; object-durable ack p99 <= 1 s applies to the profile whose commit includes the published root; the crypto-overhead row remains a measure-and-report goal. The 99.95% availability row and the 72-hour soak are qualification gates for M17.03, not baseline results. Revisions need a recorded workload and evidence rationale.
