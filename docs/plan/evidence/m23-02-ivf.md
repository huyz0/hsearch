# M23.02 evidence: IVF through the engine adapter

Provisional: every number below is from one shared 4 vCPU x86 cloud VM, release build, in-memory directory, one thread, other jobs possibly running. They are relative, not absolute, and there is no ARM run. The corpus is the same synthetic clustered one as M23.01 (64 Gaussian centres, unit-variance noise, 50,000 x 128 d, L2, 200 queries drawn around other centres). SIFT1M and GIST1M were not reachable, so the real-dataset rerun is **unrun**.

## What exists

`VectorSpec` gains an index kind: `Index::Hnsw` (the default, unchanged) or `Index::Ivf { target_cluster_size, nprobe, rerank, quantizer }`, built with `VectorSpec::ivf(..)` and `with_nprobe(..)`. The field routes to upstream's `KnnVectorsFormat::Ivf` (`lucene-ivf`, same pin `df02d694`), and `Query::Knn { nprobe }` (already in the engine since M23.01) is the per-query probe count.

- `target_cluster_size` 16 to 65,536 (default 512): the vectors a cluster is split down to. OpenSearch's `nlist` is a fixed cluster count; segments here differ in size, so the size is the parameter and `nlist` is refused with that reason.
- `quantizer`: `bbq` (default), `osq2`, `osq4`, `osq7`, `erq2` to `erq8`, `rabitq`, `auto` (picked per segment). **An IVF field always keeps codes**: there is no unquantized IVF at the pin, and the mapping refuses `none` and the HNSW `scalarN` names with that reason. "Without quantization" is served by HNSW (M23.01) or by `rerank_encoding: f32`, which keeps the full-precision vectors the final ranking reads.
- `rerank_encoding`: `f32` (default), `f16`, `bf16`, `int8` (8-bit residuals from the centroid): the bytes each reranked candidate reads.
- `nprobes` in the mapping is **required** for an IVF field and is the field's default probe count (OpenSearch's mapping parameter); `method_parameters.nprobes` overrides it per query. The engine applies the default itself (`Query::Knn { nprobe: 0 }` means the field's default), so the engine and REST paths agree. The mapping is refused without `nprobes` because upstream's automatic depth measured 0.325 recall at 50,000 vectors (below).
- `ef_search` on an IVF field is the number of candidates reranked; `nprobes` on an HNSW field is refused by name.

OpenSearch mapping parameters, and what they map to: `method.name: ivf` (engine `faiss` or `lucene`) maps to this variant; `nlist`, `encoder` (flat, pq, sq) and any unknown parameter are refused by name with a reason (`encoder`: "codes are chosen by [quantizer] ... there is no flat or pq encoder"); `nprobes` maps to the field default and is required. The stored mapping line is `knn_vector:dim=..,space=..,ivf,cs=..,np=..,rr=..,q=..` (read back, a line with `cs` or `np` out of range is refused); HNSW lines and mappings with no IVF field keep their bytes and hash.

## Update, delete and merge of write-once segments

An IVF segment is written once and never updated. A delete is an accept filter over the clusters of the segment that holds the document; a replacement is a delete plus a new document in a later segment; nothing is rewritten in place. A merge reclusters the survivors of its inputs into one new segment (upstream `merge_field`), and the deleted documents' vectors are gone from it. Tested in `crates/engine/tests/vector.rs` (`deleted_and_replaced_vectors_leave_ivf_results_before_and_after_a_merge`: four segments, a third deleted, one vector replaced; the test asserts recall at least 0.90 at 8 probed clusters before and after the merge and measured 1.0 both times, no deleted id is returned, and the replaced vector is its own nearest neighbour), and a checkpoint reopen returns the same top-10 for `bbq`, `osq4` and `auto` (`an_ivf_checkpoint_reopens_with_the_same_top_k`), including `Snapshot::open_committed`. A filter is applied inside the probe: a 5% filter returns exactly `k` hits and only matches (the test asserts recall at least 0.90 and measured 1.0).

## Recall floor

The floor M02.12 froze for quantized variants is 0.90. `every_ivf_variant_meets_its_recall_floor` (3,000 vectors, 32 d, clusters of 64, so about 47 clusters, 40 queries) asserts it for every quantizer and rerank encoding at 8 probed clusters and at the automatic depth; measured 0.9725 for all ten variants (on a corpus this small the recall is set by the clusters probed, not by the codes, so the variants are not separated by this number; the bench below and a beam of 10 show the codes differ). Seen red: routing an IVF spec to the HNSW format makes that test fail on the missing `.ivm`/`.ivp`/`.ivv` files; disabling the node's IVF detection fails the two node tests; making the engine ignore the field's default `nprobe` fails the engine default test and the node test.

`probing_fewer_clusters_costs_recall_and_more_buys_it_back` asserts 2 probes fall below 0.90, 8 reach at least 0.90 and 32 reach at least 0.98. `an_ivf_field_default_nprobe_applies_when_a_query_names_none` shows a field default of 2 gives recall under 0.90 and of 32 at least 0.98 through the engine, and that a query's own `nprobes` overrides it; the node test shows the same at a cluster boundary through the REST path.

Compared at two points. Near 0.95 recall (HNSW beam 200 at 0.9545 against IVF at 0.9725, the nearest IVF row above it) IVF builds **4.5x faster**, answers in **about 1.9x the p50 latency** in memory, and its index is **1.95x larger** (raw vectors are kept in `.ivv` as well as in the flat vector file) and peaks about 48 MiB higher. Near 0.99 recall (HNSW beam 400 at 0.9890 against IVF at 0.9985 with 32 probes) p50 is 3.07 ms against 1.63 ms, **1.9x** again. These are single runs on a shared VM, so the ratios are rough; the direction (IVF cheaper to build, larger and slower in memory) is the same at both points.

## Trade-offs and downsides

- **The automatic probe depth is too shallow on this corpus.** Without calibration upstream probes 5% of the clusters; at 50,000 vectors that is a handful and recall is 0.325. The M23.01 floor only holds at the automatic depth for the 3,000-vector test (about 47 clusters). So the automatic depth is **not** a safe default at scale: a mapping that sets `nprobes` (or a query that does) is needed, and 16 probes out of about 100 clusters (a sixth) is what reaches 0.97 here. The number of clusters to probe grows with the segment, so a fixed `nprobes` loses recall on much larger segments; there is no setting here that adapts it, and a per-segment adaptive default is not built.
- **IVF costs more bytes in memory and on disk than HNSW**: 1.95x here with `f32` rerank, 1.49x with `f16`. The reason to take it is not an in-memory win but the layout: probing a cluster is one contiguous range read of its codes and a rerank candidate is one small read, which M23.03 reads by range through the M04.02 input. In memory the quantizer choice moves p50 between 2.05 ms (osq4) and 2.61 ms (erq4) at the same probes and recall, so no code is a clear winner on this corpus; `bbq` is the default because it has the smallest codes.
- Build is much cheaper than HNSW (no graph); a segment merge reclusters from scratch (or rebalances the largest input's clusters, an upstream option), so merge cost is the clustering cost, **not measured here** at 100k to 1M vectors per segment.
- A kNN search is resolved before the rest of the query runs, as for HNSW; a `Bool` filter next to it removes hits from the top `k`.
