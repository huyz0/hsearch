# Impact-selected CI

`tools/ci.py` maps changes to checked-in package and non-Cargo ownership. The workflow runs planning/model/harness counterexamples for every change. Only allowlisted README/progress/generated roadmap/milestone/evidence changes may skip native compilation and sandbox smoke. Package changes select that package and all transitive consumers on both native Linux architectures. Debug and release tests include doctests; all features, all-target Clippy, formatting and dependency ownership remain required. Coverage tests additionally include selected production dependencies so their executable lines retain the current 90% floor. The N/A-aware Python checker always enforces per-file/per-crate floors; LLVM's additional global90 option is retained for scopes containing types, the current executable production owner. A zero-line engine-only scope reports N/A.

```sh
python3 tools/ci.py plan --base <base-sha> --head <checked-head-sha> --output impact.json
```

The checkout must match the requested head. `cargo metadata --no-deps --all-features --locked --offline` supplies every declared path edge, including optional, development, build and target-specific dependencies. Workspace package IDs, manifest directories and dependency identities must agree. The non-Cargo rules live in `ci/ownership.json`. Other Markdown, behavioral contracts and unknown files select full qualification. Behavioral contracts, task/dependency inventories, scripts, shared harness/workflow/image/toolchain/lockfile changes and any manifest change select the full matrix. Renames include both old and new paths; deletions use their previous path's current owner. An absent old owner, unknown file, missing/non-ancestor base, empty/truncated diff or incomplete graph selects the full matrix. An invalid ownership policy or checkout mismatch fails planning and cannot pass the final gate.

An over-budget plan is replaced by a full-matrix decision plus the complete change-list digest, never a truncated selective plan. The JSON plan records base/head, changed statuses/paths, graph and ownership digests, package/coverage scope, features/profiles, selected job IDs and reasons. Actions exposes that same compact JSON as a job output and prints it in the planning log. Package names are validated and passed as argument arrays, never evaluated as shell text. Selective native jobs recompute and bind the dependency graph before executing tests. No release credentials are provided; workflow permissions are contents-read and checkout credentials are not persisted. PR code runs only on ephemeral GitHub-hosted runners through `pull_request`, never `pull_request_target`.

The selected job IDs are `docs`, `linux-x64`, `linux-arm64`, `sandbox-x64` and `sandbox-arm64`. `ci-ok` uses `always()` and depends on the planner and every possible job. It requires planning success plus success for every selected job. Missing, cancelled, failed or skipped selected jobs fail. A skip is accepted only for an explicitly unselected job. The full plan requires both sandbox architectures and the entire production coverage scope. Native jobs bind their checked-out head to the plan; a stale plan cannot launch repository commands.

The reusable workflow has separate Rust and sandbox modes, each capped by a 25-minute job deadline. Sandbox work uses the [resource-leased Linux interface](sandbox.md). Unrelated package changes avoid container builds; the complete sandbox remains selected for shared/uncertain impact. This is impact selection, not the later generic changed-line/stale-profile coverage gate or crash-recovery task runner.

The fixture suite exercises docs-only, transitive and optional/build/dev/target edges, rename/deletion, missing/unknown paths and history, graph failure, stale plans and missing/cancelled/skipped job results. A real temporary Git repository and Cargo metadata exercise the selection path in the pinned Linux image. Workflow lint uses checksum-verified [actionlint 1.7.12](https://github.com/rhysd/actionlint/releases/tag/v1.7.12) locally. Hosted workflow execution and the `ci-ok` main-branch requirement must be observed before M01.06 completion; a workflow file alone is not evidence of either.
